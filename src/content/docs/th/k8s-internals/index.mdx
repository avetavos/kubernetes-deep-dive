## โมดูลนี้มีไว้ทำอะไร

ทุก module ก่อนหน้าในคอร์สนี้สอนให้คุณ **ใช้** Kubernetes เป็น เขียน manifest, `apply` ด้วย `kubectl`, อ่าน status กลับมา, scale, scheduling, security, storage และ ship ด้วย Helm/GitOps ไม่มีตอนไหนต้องรู้ว่า API server ทำอะไรกับ request จริง ๆ ระหว่างตอนที่คุณพิมพ์ `kubectl apply` กับตอนที่ object มีอยู่จริง, controller รู้ได้อย่างไรว่ามีอะไรเปลี่ยน, `kube-scheduler` plugin ที่คุณเห็นชื่อ extension point มาแล้วคืออะไรกันแน่ในเชิงโค้ด, mutating webhook กับ `ValidatingAdmissionPolicy` รันตามลำดับไหนจริง ๆ หรือ `managedFields` เก็บอะไรจริง ๆ เวลาสอง tool apply object เดียวกัน

ช่องว่างนั้นแหละคือจุดที่โค้ด/tooling Kubernetes ที่ AI เขียนพังแบบดูผิวเผินแล้วเหมือนถูก เช่น controller ที่เขียนด้วย `List` ใน `for`-loop แทนที่จะใช้ shared informer แล้ว poll เงียบ ๆ พลาด event ระหว่างรอบ, reconcile function ที่ไม่มี rate limiting จน hot-loop ซ้ำ ๆ บน error ถาวร, สมมติว่า webhook รัน "ก่อน validation เสมอ" ทั้งที่ chain จริงสลับ mutating/validating คนละแบบ, หรือ script ที่ "แก้" conflict ของ `managedFields` ด้วยการ force เอา field ทุกอันมาเป็นของตัวเองแทนที่จะอ่านว่า field ไหนขัดกันจริง ๆ ไม่มีข้อไหนเป็น syntax error ไม่มีข้อไหนถูกจับด้วย `kubectl apply --dry-run=client` ทุกข้อคือข้อเท็จจริงเรื่อง runtime ที่ module นี้พิสูจน์ให้ดูได้

Module นี้มีหน้าที่เดียว ให้ความรู้เรื่อง runtime ห้าเรื่องที่ทำให้คุณดู **โค้ดหรือ YAML ของ Kubernetes ที่คนอื่นเขียน** — controller, webhook config, scheduler profile, script เต็มไปด้วย `kubectl apply --server-side` — แล้วตอบได้ว่า

1. **เกิดอะไรขึ้นจริงกับ request ข้างใน API server และ watch ทำงานจริงอย่างไร?** (API server กับ etcd — `resourceVersion`, watch, bookmark, `410 Gone` และ etcd ในฐานะที่เดียวที่ state อยู่จริง)
2. **controller รู้ได้อย่างไรว่า "มีอะไรเปลี่ยน" โดยไม่ poll?** (controller, informer และ workqueue — Reflector → DeltaFIFO → Indexer/Lister → workqueue → reconcile ตรงจาก `client-go`)
3. **scheduler "plugin" คืออะไรจริง ๆ และรันตามลำดับไหน?** (scheduler framework — extension-point interface จริง และชื่อ plugin จริงจาก `pkg/scheduler`)
4. **mutating webhook, schema validation, validating webhook และ `ValidatingAdmissionPolicy` รันลำดับไหนจริง ๆ?** (admission chain — พิสูจน์ด้วย chain จริง, dry-run จริง และ source ที่กำหนดลำดับนี้ตรง ๆ)
5. **`managedFields` เก็บอะไรจริง ๆ และ "conflict" หมายความว่าอะไรจริง ๆ?** (Server-Side Apply internals — marker `f:`/`k:`/`v:`, `x-kubernetes-list-type` และ library `structured-merge-diff` ที่ทำให้มันทำงานได้)

ทุกข้ออ้างใน module นี้อ้างอิงจากสามอย่าง source จริงของ Kubernetes ที่ [github.com/kubernetes/kubernetes](https://github.com/kubernetes/kubernetes) tag **v1.37.0** (เวอร์ชันที่คอร์สนี้ pin ไว้) อ้างเป็นไฟล์และบรรทัดจริง, docs ทางการที่ [kubernetes.io/docs](https://kubernetes.io/docs/) หรือการรันจริงบน `kind` cluster 3 node จริง (`kind create cluster --name internals`, control-plane 1 + worker 2, Kubernetes 1.37.0) — `kubectl -v=8` trace จริง, `etcdctl get` จริง, log ของ scheduler จริง, error จริงจาก API server — วางไว้ใต้ข้ออ้างนั้นเสมอ ไม่ใช่การเดา internals

<Callout title="สรุปหนึ่งบรรทัด">
Module นี้ไม่ได้เพิ่ม API ใหม่ให้ Kubernetes — แต่อธิบายกลไกห้าอย่างที่ manifest, controller และ script ทุกอันวิ่งผ่านจริง **API server** (HTTP layer แบบ stateless คลุมอยู่บน **etcd** ที่เดียวที่ cluster state อยู่จริง — การอ่านคือ list-แล้ว-watch ที่ stamp ด้วย `resourceVersion` ไม่ใช่ poll ดิบ ๆ), **pattern informer** (Reflector → DeltaFIFO → Indexer/Lister → workqueue → reconcile ของ `client-go` ซึ่งเป็นรูปร่างเดียวกับที่ controller chain ของ Deployment/ReplicaSet ในคอร์สนี้ และ custom controller ทุกตัวที่คุณจะเขียนมีจริง ๆ), **scheduler framework** (pipeline ของ plugin ที่มีชื่อจริงบน extension point ตายตัว — `PreFilter`/`Filter`/`PostFilter`/`PreScore`/`Score`/`Reserve`/`Permit`/`PreBind`/`Bind`/`PostBind` — ไม่ใช่กล่องดำก้อนเดียว), **admission chain** (mutating admission ก่อน แล้ว schema/strategy validation แล้ว validating admission — แต่ละ phase เป็น chain ที่มีลำดับของ in-tree plugin, `MutatingAdmissionPolicy`/`ValidatingAdmissionPolicy` และ webhook เอง ลำดับถูกกำหนดตายตัวจาก source ของ API server เอง) และ **Server-Side Apply** (field ownership ต่อ manager เก็บใน `managedFields` คำนวณโดย library `structured-merge-diff` เทียบกับ marker `x-kubernetes-list-type`/`x-kubernetes-map-type` ของ OpenAPI schema จริง) ทั้งห้าอย่างอยู่บน kubernetes.io/docs หรืออ่านได้ตรง ๆ ใน `kubernetes/kubernetes` — แค่ไม่คุ้นเคย ไม่ใช่ไม่มีเอกสาร
</Callout>

## Mental Model

ทุกอย่างใน module นี้คือเรื่องเดียวกัน เล่าจากห้าจุดบน loop เดียวกัน **คุณส่ง mutation หนึ่งครั้ง API server รันมันผ่าน pipeline ตายตัว (auth, admission, validation, storage) แล้วเขียน truth เพียงชุดเดียวลง etcd ทุก component อื่น — controller, scheduler, `kubectl get -w` — รู้เรื่อง write นั้นด้วยวิธีเดียวกันคือ watch stream ที่เรียงด้วย `resourceVersion` จาก API server ตัวเดียวกันนั้น ไม่เคย poll ไม่เคยคุยกับ etcd ตรง ๆ** controller ก็แค่ "watch, queue, reconcile" ที่ต่อสายผ่านกลไก informer ของ `client-go` scheduler ก็แค่ consumer อีกตัวของ watch stream เดียวกัน ที่รัน pipeline ของ plugin ที่มีชื่อก่อนเขียนผลตัดสินใจกลับผ่าน API server ตัวเดียวกัน admission กับ Server-Side Apply ก็แค่โครงสร้างเพิ่มเติมที่ API server ใส่ลงใน write path เอง ก่อนอะไรจะไปถึง etcd พอวางข้อเท็จจริงข้อไหนใน module นี้ลงบน loop เดียวกันนี้ได้ "Kubernetes ทำงานอย่างไร" ก็เลิกเป็นเรื่องห้าเรื่องที่ต้องท่องแยกกัน

## ความเข้าใจผิดที่พบบ่อย

- **"controller poll API server เป็นช่วง ๆ เพื่อเช็คว่ามีอะไรเปลี่ยน"** [Controllers, Informers, and Workqueues](/kubernetes/th/k8s-internals/controllers-informers-and-workqueues/) พิสูจน์ตรงข้ามด้วย informer จริงที่รันอยู่ มัน list ครั้งเดียวแล้วเปิด HTTP watch connection ค้างไว้นาน ๆ แล้วตอบสนองต่อ event `ADDED`/`MODIFIED`/`DELETED` ทีละตัว ส่วน full `List` เป็นช่วง ๆ ที่คุณอาจเคยได้ยินคือ **resync** ที่เป็น safety net ไม่ใช่กลไกหลัก
- **"admission webhook ทั้งหมดรันในกลุ่มเดียวไม่แยกกัน ตามลำดับ registration"** [Admission Chain](/kubernetes/th/k8s-internals/admission-chain/) พิสูจน์ลำดับจริงตรงจาก `pkg/kubeapiserver/options/plugins.go` mutating admission (in-tree plugin แล้ว `MutatingAdmissionPolicy` แล้ว `MutatingAdmissionWebhook`) จบทั้งหมดก่อน แล้ว schema/strategy validation ถึงรัน แล้ว validating admission (in-tree, `ValidatingAdmissionPolicy`, `ValidatingAdmissionWebhook`) ถึงรัน — สอง phase ที่แยกกันจริง ไม่ใช่กลุ่มเดียว
- **"scheduler เป็นกล่องดำที่แค่เลือก node"** [Scheduler Framework](/kubernetes/th/k8s-internals/scheduler-framework/) พิสูจน์ว่ามันคือ pipeline ของ plugin ที่มีชื่อแยกกัน สลับได้แยกกัน ชื่อจริงตรงจาก `pkg/scheduler/framework/plugins/names` บน extension point ตายตัวที่นิยามใน `k8s.io/kube-scheduler/framework`
- **"`managedFields` คือ idea เดียวกับ annotation `last-applied-configuration` เก่า แค่ย้ายไปทำฝั่ง server"** [Server-Side Apply Internals](/kubernetes/th/k8s-internals/server-side-apply-internals/) พิสูจน์ว่าโครงสร้างต่างกันจริง `managedFields` คือ map ownership ต่อ manager ต่อ field คีย์ด้วย marker จริงของ OpenAPI schema (`x-kubernetes-list-type: map` เทียบกับ `atomic`) คำนวณด้วย library `structured-merge-diff` — ไม่ใช่ blob ก้อนเดียวของ "ครั้งที่แล้วฉัน apply อะไรไป"

## อ่านโค้ดที่ AI เขียน

จุดประสงค์ทั้งหมดของ module นี้คือ section นี้ ห้าครั้ง หนึ่งครั้งต่อบท ตัวอย่างระดับภาพรวมไว้ก่อน โค้ดที่ดูเหมือน controller ที่ถูกต้อง แต่ขาดสิ่งเดียวที่ทำให้มันเป็น controller จริง ๆ ไม่ใช่แค่ตัว poll
