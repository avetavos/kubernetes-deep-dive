## ไอเดียหลักในหนึ่งประโยค

Kubernetes คือ container orchestrator ที่คอยรักษา actual state ของ cluster ให้ตรงกับ state ที่คุณ declare ไว้ โดยทำงานต่อเนื่องอัตโนมัติ

## ปัญหา container ไม่ scale ให้เองอัตโนมัติ

คำสั่ง `docker run` เดี่ยว ๆ ทำงานได้ดีบน laptop หรือ server เครื่องเดียว ปัญหาจะเริ่มขึ้นทันทีที่คุณต้องใช้มากกว่าหนึ่งเครื่อง หรือมากกว่าหนึ่ง container หรือต้องการความทนทานใด ๆ เลย ถ้า process ข้างใน container crash จะไม่มีอะไร restart container นั้นให้ นอกจากคุณจะสังเกตเห็นแล้วลงมือทำเอง ถ้าอยากรัน web server 5 ตัวอยู่หลัง address เดียวกัน คุณต้องต่อสายให้เองทั้งหมด ถ้าอยากเปลี่ยน image version ใหม่โดยไม่มี downtime คุณต้องเขียน script ควบคุมลำดับการหยุด container เก่าแล้วเริ่ม container ใหม่ ให้ถูกลำดับ ถูกเครื่อง

```bash
docker run -d --name web nginx
# if this container's process dies, nothing brings it back automatically —
# you have to notice, then run `docker run` again by hand
# and there is no built-in way to run five of these behind one address
```

ทั้งหมดนี้ไม่ใช่ข้อบกพร่องของ Docker — หน้าที่ของ container runtime คือรัน container ไม่ใช่ตัดสินใจว่าควรมีกี่ตัว อยู่ที่ไหน หรือทำอะไรเมื่อ container ตาย orchestration เป็นปัญหาคนละชั้น คือเมื่อมีเครื่องหลายเครื่องกับ workload หลายชุด ต้องคอยรักษาจำนวน instance ที่ healthy ให้ถูกต้อง กระจายไปยังเครื่องที่เหมาะสม เรียกหาได้ด้วยชื่อ และอัปเดตได้อย่างปลอดภัย นี่คือปัญหาที่ Kubernetes ถูกสร้างขึ้นมาแก้

## Declarative desired state และ reconciliation loop

Kubernetes เกิดจากประสบการณ์ภายในของ Google ในการรัน container ที่สเกลใหญ่มาก ด้วยระบบชื่อ Borg และตอนนี้เป็นโครงการระดับ graduated ของ Cloud Native Computing Foundation (CNCF) เป็น open source ไม่ผูกกับ vendor ใดวันหนึ่ง และดูแลโดยชุมชนขนาดใหญ่ ไม่ใช่บริษัทเดียว

ไอเดียหลักที่คุณจะเห็นซ้ำตลอดคอร์สนี้ในทุก module คือ คุณไม่ได้บอก Kubernetes ว่าต้องทำอะไรทีละขั้นตอน แต่คุณ **declare desired state** — "ฉันอยากได้ replica 3 ตัวของ container image นี้ ฟังที่ port นี้" — แล้ว background process ชุดหนึ่งที่เรียกว่า **controller** จะคอยเฝ้าดู cluster ต่อเนื่องและลงมือทำทุกอย่างที่จำเป็นเพื่อให้ actual state ตรงกับที่คุณ declare ไว้ นี่คือ **reconciliation loop** และทำงานตลอดเวลา ไม่ใช่แค่ครั้งเดียวตอนสร้าง ถ้า Pod ตาย controller จะสังเกตเห็นว่า actual state เบี่ยงเบนไปจาก desired state แล้วสร้าง Pod ใหม่มาแทน ถ้าคุณแก้ replica count ที่ต้องการ controller จะเห็นความต่างแล้วสร้างหรือลบ Pod ให้ตรงกัน

เทียบกับเป้าหมายเดียวกัน "รัน nginx รักษา replica 3 ตัวให้ healthy" ที่เขียนแบบ declarative เป็น Kubernetes Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.31
          ports:
            - containerPort: 80
```

คุณส่ง manifest นี้ให้ cluster แค่ครั้งเดียว จากนั้นถ้า replica ตัวไหน crash ถูก evict หรือ node ที่อยู่หายไป controller จะสร้าง Pod ใหม่ขึ้นมาให้จำนวนกลับเป็น 3 โดยคุณไม่ต้องทำอะไรเพิ่ม การ roll out image ใหม่ก็ declarative เหมือนกัน แค่เปลี่ยน `image: nginx:1.31` เป็น tag ใหม่แล้ว apply ซ้ำ Deployment controller จะทยอยแทนที่ Pod ให้เองทีละส่วน

## พิสูจน์ reconciliation loop ด้วย timestamp จริง

คำกล่าวอ้างข้างบน — "controller สร้าง Pod มาแทน โดยคุณไม่ต้องทำอะไรเพิ่ม" — ไม่ใช่สิ่งที่ต้องเชื่อเฉย ๆ บน Deployment จริงที่มี 3 replica รันอยู่แล้ว ลบ Pod หนึ่งตัวด้วยมือแล้วเช็ก creation timestamp ทันที

```text
$ kubectl get pods -l app=web -o custom-columns='NAME:.metadata.name,CREATED:.metadata.creationTimestamp'
NAME                   CREATED
web-69d5569566-fmcq2   2026-09-26T08:33:54Z
web-69d5569566-gcqh4   2026-09-26T08:33:54Z
...

$ kubectl delete pod web-69d5569566-fmcq2
pod "web-69d5569566-fmcq2" deleted

$ kubectl get pods -l app=web -o custom-columns='NAME:.metadata.name,STATUS:.status.phase,CREATED:.metadata.creationTimestamp'
NAME                   STATUS    CREATED
web-69d5569566-45pp7   Running   2026-09-26T08:35:08Z
web-69d5569566-gcqh4   Running   2026-09-26T08:33:54Z
...
```

การ delete กับ `creationTimestamp` ของตัวแทนคือ**วินาทีเดียวกัน** ไม่มีใครรันคำสั่งที่สองเลย — watch ของ ReplicaSet controller (พิสูจน์ในบทถัดไป) เห็น replica count ที่แท้จริงลดจาก 3 เหลือ 2 แล้วสร้าง Pod ใหม่ทันทีเพื่อให้กลับไปเป็น 3 ตามที่ declare ไว้ นี่คือ reconciliation loop ในระดับที่ลึกกว่าคำอุปมา ไม่ใช่ "Kubernetes จะสังเกตเห็นในที่สุด" แต่คือ controller ที่ตอบสนองภายในวินาทีเดียวกัน พิสูจน์ได้จริงบน cluster จริง

## Cluster ประกอบด้วย control plane และ node

Kubernetes cluster มีเครื่องสองแบบ **control plane** คือสมองของ cluster เก็บ desired state ตัดสินใจเรื่อง scheduling และรัน controller ที่ขับเคลื่อน reconciliation — [บทถัดไป](/kubernetes/th/foundations/architecture-control-plane-and-nodes/) จะลงลึกถึง component ของตัวเอง รวมถึงวิธีที่ controller เหล่านั้น watch การเปลี่ยนแปลงจริง ๆ และ state เอง คือ etcd อยู่ตรงไหนจริง ๆ ส่วน **node** คือ worker คือเครื่อง (physical หรือ virtual) ที่รัน container ของคุณจริง ๆ โดยห่อหุ้มอยู่ใน unit ที่เล็กที่สุดที่ deploy ได้ของ Kubernetes เรียกว่า **Pod** ซึ่งจะแนะนำอย่างจริงจังใน [module workloads](/kubernetes/th/workloads/pods-the-atomic-unit/)

## Kubernetes ไม่ใช่อะไร

การเห็น orchestrator ซ่อม Pod ที่ crash ให้เองครั้งหนึ่งก็ทำให้ให้เครดิตมันเกินได้ง่าย ๆ มีขอบเขตบางอย่างที่ควรพูดให้ชัด เพราะ architecture proposal ที่ generate มามักจะทำให้เส้นแบ่งพวกนี้เบลอ

- **ไม่ใช่ PaaS** Kubernetes schedule และรัน container ที่คุณ build มาแล้ว มันไม่ build application ให้คุณ ไม่จัดการ source repository ของคุณ และไม่ตัดสินใจ deployment pipeline ให้คุณ — นั่นเป็นหน้าที่ของระบบ CI/CD ที่วางทับไว้ข้างบน (คอร์สนี้ครอบคลุมชั้นนั้นใน [module GitOps](/kubernetes/th/production-and-ecosystem/gitops-and-cicd-for-kubernetes/))
- **ไม่มี CI ในตัว** ไม่มี primitive "รัน test suite ของฉัน" อยู่ใน Kubernetes เองที่ไหนเลย Job หรือ CronJob รัน container ที่บังเอิญไปรัน test ได้ แต่ pipeline ที่ตัดสินใจว่าเมื่อไหร่จะ build, test และ deploy คือ tooling ภายนอก ไม่ใช่ feature ของ cluster
- **Ingress API แบบเดิมแช่แข็งแล้ว ไม่ได้พัฒนาต่อ** deep review ของคอร์สนี้เองยืนยันแล้ว Ingress API ของ `networking.k8s.io` แช่แข็งแล้วจริง ๆ เพื่อให้ **Gateway API** ตัวใหม่มาแทน และ `ingress-nginx` เองก็กำลังจะ retire (มีนาคม 2026) — งานใหม่ในพื้นที่นี้เล็งไปที่ Gateway API ไม่ใช่ feature ใหม่ของ Ingress

## อ่านโค้ดที่ AI เขียน

ตอนรีวิว architecture proposal ที่ generate มา หรือคำกล่าวอ้างว่า Kubernetes จัดการอะไรให้อัตโนมัติ เช็กสิ่งเหล่านี้

- "Kubernetes จะ build และ deploy โค้ดจาก git push ให้" ที่ถูกนำเสนอเป็น built-in feature — พิสูจน์ข้างบนแล้วว่า Kubernetes รัน container ที่คุณส่งให้ pipeline build-and-deploy เป็นเครื่องมือแยกเสมอ (ระบบ CI, Argo CD/Flux สำหรับ GitOps) วางทับไว้ข้างบน ไม่เคยเป็น primitive ของ cluster
- diagram หรือ plan ที่ generate มาแล้วเอา test suite ไปวางไว้ "ใน Kubernetes" ตรง ๆ โดยไม่มีระบบ CI แยก — พิสูจน์ข้างบนแล้วว่าไม่มี primitive CI ในตัว Job ที่รัน `npm test` ก็แค่ Job ไม่ใช่ตัวแทน pipeline ที่ตัดสินใจว่า*เมื่อไหร่*จะรัน และ*จะทำอะไร*กับผลลัพธ์
- คำแนะนำให้สร้าง traffic-routing feature ใหม่บน `Ingress` API แบบเดิมต่อไป — พิสูจน์ใน deep review ที่คอร์สนี้สร้างขึ้นบนนั้นแล้วว่า Ingress แช่แข็งและ `ingress-nginx` กำลังจะ retire งานใหม่ควรอยู่บน Gateway API แทน
- "reconciliation loop รันเป็นช่วง ๆ ประมาณทุกไม่กี่วินาที/นาที" เป็นคำอธิบายว่า self-healing ทำงานยังไง — พิสูจน์ข้างบนด้วย timestamp จริงแล้วว่า trigger จริงคือ state ที่ถูก watch เปลี่ยน ไม่ใช่ timer

## Mental Model

ทุก feature ที่คอร์สนี้ครอบคลุม ในทุก module ถัดไป คือตัวอย่างของไอเดียเดียวกันเป๊ะ คือมีบางอย่าง declare desired state แล้ว controller ขับเคลื่อน actual state ให้ไปหามันตลอดเวลา "3 replica" ของ ReplicaSet กับ target CPU percentage ของ HorizontalPodAutoscaler คือ pattern เดียวกันคนละชั้น — บทนี้แค่พิสูจน์ pattern นั้นครั้งเดียวด้วยนาฬิกาจับเวลา เพื่อให้ "Deployment controller ทยอยแทนที่ Pod ให้เองทีละส่วน" ใน module ถัดไป อ่านเป็นข้อเท็จจริงที่คุณเคยเห็นเกิดขึ้นแล้ว ไม่ใช่คำกล่าวอ้างที่ต้องเชื่อเฉย ๆ

## ข้อแลกเปลี่ยน

| ทางเลือก | ข้อดี | ต้นทุน |
|---|---|---|
| Declarative desired state + reconciliation | self-healing เกิดขึ้นอัตโนมัติและต่อเนื่อง พิสูจน์ข้างบนด้วย timestamp วินาทีเดียวกันจริง คุณอธิบายเป้าหมาย ไม่ใช่ขั้นตอน | คุณเสีย control ระดับละเอียดเหนือลำดับ operation ที่แท้จริงไป — controller เป็นคนตัดสินใจว่า *ยังไง* ไม่ใช่แค่ *จะทำไหม* |
| Kubernetes เป็น "แค่" orchestrator (ไม่มี CI/PaaS ในตัว) | ประกอบร่างได้ — เอา CI tool, GitOps tool, image builder อะไรก็ได้ที่คุณใช้อยู่แล้วมาต่อ | มีชิ้นส่วนต้องต่อเองเยอะขึ้น ไม่มีอะไรมาพร้อมแบบ batteries-included ให้ตลอดทางจาก git push ถึง Pod ที่รันอยู่ |
| Gateway API แทน Ingress API ที่แช่แข็งแล้วสำหรับงานใหม่ | พัฒนาต่อเนื่องอยู่ routing แสดงออกได้มากกว่า (พิสูจน์จริงใน deep review ของคอร์สนี้เอง) | setup ที่ใช้ Ingress อยู่แล้วต้อง migrate อย่างตั้งใจ ไม่ใช่ upgrade อัตโนมัติ |

## ความเข้าใจผิดที่พบบ่อย

- **"Kubernetes build และ deploy โค้ดจาก git push ให้"** พิสูจน์ข้างบนแล้วว่ามันแค่ reconcile container และ object ที่คุณ declare ระบบ CI เป็นคน build image GitOps tool เป็นคน apply ผลลัพธ์ — Kubernetes เองไม่ทำทั้งสองอย่าง
- **"reconciliation loop รันตาม timer เช็กทุกไม่กี่วินาที"** พิสูจน์ข้างบนด้วย timestamp จริงแล้วว่า Pod ที่ถูกลบมีตัวแทนถูกสร้างในวินาทีเดียวกัน ขับเคลื่อนด้วย watch บนการเปลี่ยนแปลงจริง ไม่ใช่ polling interval
