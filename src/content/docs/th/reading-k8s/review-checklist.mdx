## apiVersion & รูปร่าง

- `apiVersion` ยัง resolve ได้บนคลัสเตอร์ที่คุณ deploy จริงหรือไม่ (`kubectl api-resources`, `kubectl explain <kind>`)? `extensions/v1beta1`, `batch/v1beta1`, และ `networking.k8s.io/v1beta1` ถูกถอดออกทั้งหมดแล้ว ดู **[AI Bug Catalog](/kubernetes/th/reading-k8s/ai-bug-catalog/)** ข้อ 1–3
- ยังมีที่ไหนอ้างถึง `kind: PodSecurityPolicy` อยู่หรือไม่? ถูกลบไปตั้งแต่ Kubernetes 1.25 — ตัวแทนคือ label บน Namespace บวกกับ Pod Security Admission ดูข้อ 4
- `Ingress` ใช้รูปร่างปัจจุบัน `backend.service.name`/`port.number` (พร้อมตั้ง `pathType`) ไม่ใช่ `backend.serviceName`/`servicePort` ที่ถูกลบไปแล้วหรือไม่? ดูข้อ 3
- `HorizontalPodAutoscaler` ปน field ของ `autoscaling/v1` (`targetCPUUtilizationPercentage`) กับ field ที่มีแค่ใน `autoscaling/v2` (`metrics`, `behavior`) ใน object เดียวกันหรือไม่? เป็น `BadRequest` จริงฝั่ง server ปัจจุบัน ดูข้อ 5

## Workload

- มีใครพยายามเปลี่ยน `spec.selector` ของ Deployment ที่ *มีอยู่แล้ว* หรือไม่? เป็นการปฏิเสธ `field is immutable` จริงและปัจจุบัน ดู **[AI Bug Catalog](/kubernetes/th/reading-k8s/ai-bug-catalog/)** ข้อ 6 และ **[Deployments and ReplicaSets](/kubernetes/th/workloads/deployments-and-replicasets/)**
- Pod template ของ Job เคยตั้ง `restartPolicy: Always` หรือไม่? มีแค่ `OnFailure`/`Never` ที่ valid — ดูข้อ 7 สำหรับการปฏิเสธจริงและปัจจุบัน
- `strategy.rollingUpdate` ของ Deployment ตั้งทั้ง `maxUnavailable: 0` และ `maxSurge: 0` หรือไม่? เป็นการปฏิเสธค่า invalid จริงและปัจจุบัน ไม่ใช่ rollout ที่ค้างซึ่งพบทีหลัง ดูข้อ 8
- `serviceName` ของทุก StatefulSet ชี้ไปที่ Service ที่มีอยู่จริง **และ** headless (`clusterIP: None`) หรือไม่? ไม่ถูกตรวจสอบตอนสร้าง — ดูข้อ 9 พิสูจน์ด้วย `NXDOMAIN` จริง
- `concurrencyPolicy` ตั้งไว้อย่างตั้งใจในทุก CronJob หรือปล่อยไว้ที่ค่า default `Allow` แบบเงียบ ๆ? ดูข้อ 10 พิสูจน์ด้วย Job ที่ทับซ้อนกันจริง
- `selector` ของทุก Service ตรงกับ `labels` จริงของ Pod template หรือไม่ — เช็กโดยตรง ไม่ใช่แค่สมมติ? ดูข้อ 11 พิสูจน์ด้วย `EndpointSlice` ที่ว่างเปล่าจริง

## Scheduling

- ถ้า HPA เล็งไปที่ workload โดยดู CPU/memory utilization container ของ workload นั้นตั้ง `resources.requests` หรือไม่? ดู **[AI Bug Catalog](/kubernetes/th/reading-k8s/ai-bug-catalog/)** ข้อ 12 พิสูจน์ด้วย `FailedGetResourceMetric` จริง และ **[Horizontal Pod Autoscaling](/kubernetes/th/scheduling-and-scaling/horizontal-pod-autoscaling/)**
- `minAvailable` (หรือ `maxUnavailable`) ของทุก PodDisruptionBudget เหลือที่ว่างจริงต่ำกว่าจำนวน replica เต็มหรือไม่? ดูข้อ 13 พิสูจน์ด้วยการ drain ที่ถูกบล็อกถาวรจริง และ **[Pod Disruption & Cluster Autoscaling](/kubernetes/th/scheduling-and-scaling/pod-disruption-and-cluster-autoscaling/)**

## Networking

- `policyTypes` ของ NetworkPolicy ระบุครบทุกทิศทางที่ชื่อหรือ comment ของมันอ้างว่าจำกัดหรือไม่? การละ `Egress` ทำให้ทิศทางนั้นไม่ถูกจำกัดเลย ไม่ใช่ "ครอบคลุมโดย default" ดู **[AI Bug Catalog](/kubernetes/th/reading-k8s/ai-bug-catalog/)** ข้อ 14 พิสูจน์ด้วย curl ที่ไม่ถูกบล็อกจริง
- ถ้า NetworkPolicy เป็น default-deny จริง (`policyTypes: [Ingress, Egress]`, ไม่มี rule) มันยัง allow egress ไปยังตัวให้บริการ DNS ของคลัสเตอร์ (`kube-system`, UDP/TCP 53) อย่างชัดเจนหรือไม่? ไม่งั้นทุกการ lookup hostname — รวมถึงชื่อ Service ของ Kubernetes เอง — จะพังไปด้วย ดูข้อ 15 พิสูจน์ด้วย `nslookup` ที่ timeout จริง

## Storage & configuration

- volume แบบ `hostPath` เก็บข้อมูลที่ควรรอดจากการ reschedule ไปยัง node อื่นหรือไม่? พิสูจน์แล้วว่าทิ้งข้อมูลไว้แบบเงียบ ๆ — ดู **[AI Bug Catalog](/kubernetes/th/reading-k8s/ai-bug-catalog/)** ข้อ 16
- มีอะไร — comment, ชื่อตัวแปร, runbook — เรียกเนื้อหาของ `Secret` ว่า "encrypted" หรือไม่? field `data` ของมันแค่ base64-encode เท่านั้น ใครก็ตามที่มีสิทธิ์ `get secret` ธรรมดาก็ decode กลับได้ทันที ดูข้อ 17

## Security

- `securityContext.privileged: true` (หรือ `hostNetwork`/`hostPID`/`hostIPC`) ปรากฏเป็นวิธีแก้ permission error ในคอนเทนเนอร์ แทนที่จะเป็น capability หรือ field เฉพาะที่จำเป็นจริง ๆ หรือไม่? ดู **[AI Bug Catalog](/kubernetes/th/reading-k8s/ai-bug-catalog/)** ข้อ 18 และ **[Pod & Cluster Security](/kubernetes/th/observability-and-security/pod-and-cluster-security/)** สำหรับข้อความปฏิเสธจริงของ Pod Security Admission ที่มันสร้าง
- Linux capability เคยถูก drop หรือไม่ (`capabilities.drop: ["ALL"]`) โดยเพิ่มกลับมาเฉพาะสิ่งที่จำเป็นจริงผ่าน `capabilities.add`? ดูข้อ 19
- `automountServiceAccountToken: false` ตั้งไว้บน workload ที่ไม่เคยเรียก API server ของ Kubernetes เลยหรือไม่? ดูข้อ 20
- ServiceAccount ของ workload เคยถูกผูกกับ `cluster-admin` แทนที่จะเป็น `Role`/`ClusterRole` ที่จำกัดขอบเขตแคบ ๆ หรือไม่? ดูข้อ 21 พิสูจน์ด้วย `kubectl auth can-i` จริงที่แสดงขอบเขตทั่วทั้งคลัสเตอร์ และ **[RBAC & Service Accounts](/kubernetes/th/observability-and-security/rbac-and-service-accounts/)**

## Observability

- ทุก Deployment ที่อยู่หลัง Service มี `readinessProbe` ที่เช็ก endpoint ของแอปจริง ไม่ใช่แค่ "process กำลังรัน" หรือไม่? ดู **[AI Bug Catalog](/kubernetes/th/reading-k8s/ai-bug-catalog/)** ข้อ 22 พิสูจน์ด้วย `Connection refused` จริงระหว่าง startup และ **[Probes: Liveness, Readiness, Startup](/kubernetes/th/observability-and-security/probes-liveness-readiness-startup/)**
- `livenessProbe` กับ `readinessProbe` เคยชี้ไปที่ endpoint เดียวกันโดยไม่มี `startupProbe` รองรับการ warm-up ที่ช้าหรือไม่? ดูข้อ 23 พิสูจน์ด้วย restart loop ที่เกิดจากตัวเองจริง
- คำสั่ง debug สมมติว่า `kubectl exec -it <pod> -- sh` ใช้ได้เสมอ แม้กับ image แบบ minimal หรือ distroless ที่ไม่มี shell เลยหรือไม่? `kubectl debug --target` (ephemeral container, GA ตั้งแต่ 1.25) คือวิธีแก้จริง ดูข้อ 24 และ **[Logging & Metrics](/kubernetes/th/observability-and-security/logging-and-metrics/)**

## Tooling

- `kubectl apply --dry-run=server` (ไม่ใช่แค่ `--dry-run=client`) ถูกรันกับ API server จริงก่อนที่จะเชื่อว่าอะไรใน checklist นี้ "น่าจะโอเค" หรือไม่? `--dry-run=client` ไม่ติดต่อ server เลย และพลาด error ของ discovery/admission/strict-decoding ทุกอันที่ checklist นี้พึ่งพา ดู **[Verification Tools](/kubernetes/th/reading-k8s/verification-tools/)**
- CI รัน schema validator จริง (`kubeconform`, `kube-linter`, `polaris`, หรือ `tools/verify-manifests.mjs` ของคอร์สนี้เอง) กับทุก manifest ไม่ใช่แค่คนไล่ดูด้วยตาหรือไม่? ดู **[Verification Tools](/kubernetes/th/reading-k8s/verification-tools/)**
- โหมด `warn` ของ Pod Security Admission (ไม่ใช่แค่ `enforce`) ถูกใช้เป็น linter ที่ทำงานจริง — เช็กทุกครั้งที่ apply แม้ใน namespace ที่ยังไม่พร้อม enforce `restricted` หรือไม่? ดู **[Pod & Cluster Security](/kubernetes/th/observability-and-security/pod-and-cluster-security/)**
