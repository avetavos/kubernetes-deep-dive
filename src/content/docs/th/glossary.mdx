ศัพท์ของ Kubernetes ครอบคลุมหลายชั้นพร้อมกัน: workload object (Pod, Deployment, StatefulSet, DaemonSet, Job) ที่บอกว่าอะไรควรรัน, cluster service (Service, Ingress, Gateway API, NetworkPolicy) ที่บอกว่า traffic ไปถึงมันได้ยังไง, storage กับ config object (ConfigMap, Secret, PV/PVC, StorageClass) ที่บอกว่ามันต้องการอะไร และ control plane (API server, etcd, controller, scheduler) ที่ reconcile ทุกอย่างพวกนี้เข้าหา state ที่เราประกาศไว้อยู่ตลอดเวลา ทับซ้อนอยู่บนนี้คือ RBAC กับ admission control สำหรับควบคุมว่าใครทำอะไรได้ และ toolchain — `kubectl`, Helm, GitOps — สำหรับ operate cluster จริง ๆ เวลาอ่านบทเรียนแล้วเจอคำที่ไม่คุ้น หรือไม่แน่ใจว่ายังใช้ได้อยู่กับ Kubernetes 1.37 ไหม ให้กลับมาดูที่นี่

## A

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| admission webhook | callback แบบ HTTP ที่ API server เรียกระหว่าง admission (validating และ/หรือ mutating) ก่อนจะบันทึก object ลงไป `ValidatingAdmissionPolicy`/`MutatingAdmissionPolicy` ครอบคลุมหลายเคสในคลัสเตอร์ได้โดยไม่ต้องมี webhook เอง แต่ Kyverno กับ Gatekeeper ก็ยังรันเป็น webhook สำหรับอะไรก็ตามที่ policy แบบ CEL แสดงออกมาไม่ได้ | [Pod & Cluster Security](/kubernetes/th/observability-and-security/pod-and-cluster-security/) |
| affinity / anti-affinity | `podAffinity` จะ schedule Pod ให้อยู่ *ใกล้* กับ Pod ที่ match label selector (node/zone/topology domain เดียวกัน) ส่วน `podAntiAffinity` จะ schedule ให้อยู่ *ห่าง* จากมัน — ทั้งคู่รองรับทั้งแบบ `requiredDuringSchedulingIgnoredDuringExecution` (บังคับ) และ `preferred...` (ขอไว้เฉย ๆ) และทั้งคู่ถูกประเมินแบบ all-or-nothing ต่อหนึ่ง term | [Node Affinity, Taints & Tolerations](/kubernetes/th/scheduling-and-scaling/node-affinity-taints-and-tolerations/) |
| annotation | key/value pair บน metadata ของ object ที่ไม่ได้ใช้ระบุตัวตน มีไว้ให้ tooling หรือ library แปะข้อมูลอะไรก็ได้เข้าไป — ต่างจาก label ตรงที่ annotation ไม่เคยถูกใช้เป็นเป้าหมายของ selector | [kubectl & Declarative YAML](/kubernetes/th/foundations/kubectl-and-declarative-yaml/) |
| API server (`kube-apiserver`) | ประตูหน้าเดียวของคลัสเตอร์ Kubernetes ทั้งหมด: ทุกการอ่านและเขียน — จาก `kubectl`, controller หรือ component อื่นของ control plane — ผ่านมันทั้งหมด และมันคือ component เดียวใน control plane ที่คุยกับ `etcd` ตรง ๆ | [Architecture: Control Plane & Nodes](/kubernetes/th/foundations/architecture-control-plane-and-nodes/) |

## B–C

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| bound token (ServiceAccount) | ตั้งแต่ Kubernetes 1.22 token ของ ServiceAccount เป็น JWT อายุสั้น ผูก audience และ rotate อัตโนมัติ ได้มาจาก `TokenRequest` API (หรือ projected volume แบบ `serviceAccountToken` ที่มี `expirationSeconds`) — ไม่มีการสร้าง Secret token อายุยืนให้อัตโนมัติอีกต่อไป | [RBAC & Service Accounts](/kubernetes/th/observability-and-security/rbac-and-service-accounts/) |
| CEL (Common Expression Language) | ภาษา expression ที่ `ValidatingAdmissionPolicy` กับ `MutatingAdmissionPolicy` ใช้เขียนกฎ validate/mutate ตรง ๆ กับ object ที่เข้ามา (`object.spec...`) แทนที่จะต้องส่ง webhook server ไปรันเช็คแบบเดียวกัน | [Pod & Cluster Security](/kubernetes/th/observability-and-security/pod-and-cluster-security/) |
| Chart (Helm) | directory ของ manifest ของ Kubernetes ที่ template ไว้ พร้อม metadata `Chart.yaml` และค่า default `values.yaml` — หน่วยที่ Helm packages, versions และติดตั้งออกมาเป็น Release | [Helm Package Management](/kubernetes/th/production-and-ecosystem/helm-package-management/) |
| CNI (Container Network Interface) | plugin interface ที่ต่อ networking ของ Pod ให้จริง ๆ และ — สำหรับ plugin ที่ implement มันไว้ (Calico, Cilium และตัวอื่น ๆ) — บังคับใช้ `NetworkPolicy` ด้วย; CNI ที่ไม่ implement การบังคับใช้ policy จะรับ object `NetworkPolicy` ไว้เฉย ๆ โดยไม่บล็อก traffic อะไรเลย | [Network Policies](/kubernetes/th/networking/network-policies/) |
| Cluster Autoscaler | เพิ่มหรือลด Node ทั้งตัวตามแรงกดดันในการ schedule Pod — scale up เมื่อ Pod ค้างอยู่ที่ `Pending` เพราะ capacity ไม่พอ, scale down Node ที่ใช้งานน้อยด้วยการ cordon แล้ว drain ก่อน (เป็น voluntary disruption จึงเคารพ PodDisruptionBudget ต่างจาก preemption) | [Pod Disruption & Cluster Autoscaling](/kubernetes/th/scheduling-and-scaling/pod-disruption-and-cluster-autoscaling/) |
| ConfigMap | object ระดับ namespace ที่เก็บข้อมูล configuration แบบ key/value ที่ไม่ลับ ให้ Pod ใช้เป็น environment variable, ค่า `env` ทีละตัว หรือ mount เป็น volume ของไฟล์ | [ConfigMaps & Secrets](/kubernetes/th/storage-and-config/configmaps-and-secrets/) |
| containerd | container runtime ที่ kubelet คุยด้วยผ่าน CRI เพื่อ pull image และ start/stop container จริง ๆ บน Node — เป็น runtime default ของ kind, managed Kubernetes ส่วนใหญ่ และคลัสเตอร์ของคอร์สนี้ | [Architecture: Control Plane & Nodes](/kubernetes/th/foundations/architecture-control-plane-and-nodes/) |
| controller | control loop ที่ watch object หนึ่งชนิด (หรือหลายชนิด) เทียบ observed state กับ desired state แล้วยิง API call เพื่อขยับคลัสเตอร์เข้าหา desired state — เป็น pattern ที่ workload controller built-in ทุกตัวและ Operator ทุกตัวใช้ | [What is Kubernetes?](/kubernetes/th/foundations/what-is-kubernetes/) |
| cordon / drain | `kubectl cordon <node>` ทำเครื่องหมายว่า Node นั้น unschedulable โดยไม่แตะอะไรที่รันอยู่แล้ว; `kubectl drain <node>` เพิ่มการ evict Pod ที่มีอยู่ผ่าน Eviction API (ที่เคารพ PodDisruptionBudget) — คู่นี้ใช้ก่อนจะบำรุงรักษาหรือแทนที่ Node แบบ voluntary | [Pod Disruption & Cluster Autoscaling](/kubernetes/th/scheduling-and-scaling/pod-disruption-and-cluster-autoscaling/) |
| CoreDNS | DNS server ของคลัสเตอร์: เป็น Deployment ที่รันอยู่ใน `kube-system` ตอบ query `<service>.<namespace>.svc.cluster.local` (และ DNS ของ Pod) ด้วยการ watch Service กับ Endpoints/EndpointSlice ทำให้ client เรียก Service ด้วยชื่อได้แทนที่จะต้องใช้ ClusterIP | [DNS & Service Discovery](/kubernetes/th/networking/dns-and-service-discovery/) |
| CronJob | สร้าง Job ตามตารางเวลา (syntax แบบ cron มาตรฐาน) ควบคุมด้วย `concurrencyPolicy` (`Allow`/`Forbid`/`Replace`), `startingDeadlineSeconds` สำหรับตารางที่พลาดไป และ history limit ของความสำเร็จ/ความล้มเหลวแยกกัน | [Jobs & CronJobs](/kubernetes/th/workloads/jobs-and-cronjobs/) |
| CRD (CustomResourceDefinition) | ลงทะเบียน object Kind ใหม่เอี่ยมกับ API server พร้อม schema แบบ OpenAPI v3 สำหรับ validate — พอลงแล้ว `kubectl get`/`apply`/`watch` ใช้กับมันได้เหมือน object built-in ทุกประการ และมันถูกเก็บใน `etcd` แบบเดียวกัน | [Operators & Custom Resources](/kubernetes/th/production-and-ecosystem/operators-and-custom-resources/) |
| CRI (Container Runtime Interface) | interface แบบ gRPC ระหว่าง kubelet กับ container runtime (containerd, CRI-O) — เป็นตัวที่ทำให้ kubelet จัดการ container ได้โดยไม่ต้อง hardcode API ของ runtime ตัวใดตัวหนึ่ง | [Architecture: Control Plane & Nodes](/kubernetes/th/foundations/architecture-control-plane-and-nodes/) |
| CSI (Container Storage Interface) | plugin interface (GA ตั้งแต่ Kubernetes 1.13) ที่ให้ driver ของ vendor storage เสียบเข้ากับ Kubernetes ได้โดยไม่ต้องอยู่ใน tree `kubernetes/kubernetes` หลัก — เกือบทุก `StorageClass` ใน production ระบุ `provisioner` เป็น driver แบบ CSI | [PVs, PVCs & Storage Classes](/kubernetes/th/storage-and-config/persistent-volumes-claims-and-storage-classes/) |
| custom resource | *instance* ของ Kind ที่ CRD กำหนดไว้ — CRD คือ schema ส่วน custom resource คือ object หนึ่งตัวที่ตรงกับ schema นั้น เหมือนกับที่ Pod เป็น instance ของ Kind `Pod` ที่ built-in มาให้ | [Operators & Custom Resources](/kubernetes/th/production-and-ecosystem/operators-and-custom-resources/) |

## D–E

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| DaemonSet | รัน Pod หนึ่งชุดบนทุก Node ที่ match node selector (ถ้ามี) เพิ่มหรือลบ Pod ให้อัตโนมัติเมื่อ Node เข้าหรือออกจากคลัสเตอร์ — รูปแบบสำหรับ agent ประจำ Node อย่าง log shipper หรือ CNI plugin | [StatefulSets & DaemonSets](/kubernetes/th/workloads/statefulsets-and-daemonsets/) |
| Deployment | จัดการ ReplicaSet (และระหว่าง update ก็จัดการ ReplicaSet เก่ากับใหม่พร้อมกัน) เพื่อให้ rolling update และ rollback แบบ declarative และมี version ให้กับ workload แบบ stateless — chain ความเป็นเจ้าของคือ Deployment → ReplicaSet → Pod | [Deployments & ReplicaSets](/kubernetes/th/workloads/deployments-and-replicasets/) |
| dry-run (client vs server) | `kubectl apply --dry-run=client` แค่ render manifest ในเครื่อง ไม่มีการส่งไปหา server เลย; `--dry-run=server` ส่ง request ผ่าน chain validation และ admission ของ API server ทั้งหมด (เลยจับ rejection จริงจาก schema หรือ policy ได้) โดยไม่บันทึก object ลงจริง | [kubectl & Declarative YAML](/kubernetes/th/foundations/kubectl-and-declarative-yaml/) |
| emptyDir | volume ที่ถูกสร้างขึ้นแบบว่างเปล่าตอน Pod ถูก schedule และถูกลบถาวรตอน Pod ถูกเอาออกจาก Node — เป็นพื้นที่ scratch ที่แชร์กันระหว่าง container ใน Pod เดียวกัน ไม่ใช่ storage แบบถาวร | [Volumes & Volume Types](/kubernetes/th/storage-and-config/volumes-and-volume-types/) |
| Endpoints (deprecated) | list ของ IP ของ Pod ที่รองรับ Service แบบเดิม เป็น object เดียวต่อ Service หนึ่งตัว (`core/v1`) มันไม่ shard เลยขยายได้ไม่ดีถ้ามี backend เกินสองสามร้อยตัว — EndpointSlice (GA ตั้งแต่ Kubernetes 1.21) เป็นตัวแทนที่แนะนำ ซึ่ง kube-proxy และ CoreDNS ก็อ่านมันอยู่แล้ว | [Services: ClusterIP, NodePort, LoadBalancer](/kubernetes/th/networking/services-clusterip-nodeport-loadbalancer/) |
| EndpointSlice | ตัวแทน Endpoints ที่ scale ได้และ shard ได้ (`discovery.k8s.io/v1`, GA ตั้งแต่ 1.21): Pod ที่รองรับ Service หนึ่งตัวถูกแบ่งเก็บใน EndpointSlice หลายตัว (จำกัดจำนวนต่อ slice) แทนที่จะเป็น object Endpoints เดียวที่โตขึ้นเรื่อย ๆ และทั้ง kube-proxy กับ CoreDNS ก็ watch ตัวนี้โดยตรง | [Services: ClusterIP, NodePort, LoadBalancer](/kubernetes/th/networking/services-clusterip-nodeport-loadbalancer/) |
| ephemeral container | container แบบใช้แล้วทิ้ง (GA/stable ตั้งแต่ Kubernetes 1.25) ที่แปะเข้าไปใน Pod ที่ *กำลังรันอยู่แล้ว* ผ่าน `kubectl debug` แชร์ process namespace กับ container เป้าหมายเพื่อ troubleshoot — มันไม่ restart Pod เลยและไม่สามารถเพิ่มเข้าไปใน Pod spec เดิมได้ | [Logging & Metrics](/kubernetes/th/observability-and-security/logging-and-metrics/) |
| etcd | key-value store แบบ distributed ที่เป็น single source of truth ของคลัสเตอร์ — ทุก object ที่ API server เสิร์ฟถูกอ่านและเขียนจาก `etcd` และมีแค่ API server เท่านั้นที่คุยกับมันตรง ๆ | [Architecture: Control Plane & Nodes](/kubernetes/th/foundations/architecture-control-plane-and-nodes/) |
| `extensions/v1beta1` (removed) | API group ที่ยังไม่ stable ที่ resource ยุคแรกของ Kubernetes (Deployment, DaemonSet, ReplicaSet, NetworkPolicy) เคยอยู่ชั่วคราว หยุดถูกเสิร์ฟไปตั้งแต่ Kubernetes 1.16 (ย้ายไป `apps/v1`/`networking.k8s.io/v1`) ส่วน Ingress เองที่อยู่ใต้ `extensions/v1beta1`/`networking.k8s.io/v1beta1` ก็ถูกเอาออกใน 1.22 — manifest ที่ใช้มันวันนี้จะถูก reject ตรง ๆ ไม่ใช่ downgrade แบบเงียบ ๆ | [kubectl & Declarative YAML](/kubernetes/th/foundations/kubectl-and-declarative-yaml/) |

## F–G

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| field manager / `managedFields` | Server-Side Apply จะติดตามว่า *ใคร* เป็นเจ้าของ *field ไหน* ของ object ไว้ใน `metadata.managedFields` โดย key ด้วยชื่อ field manager (ค่า default ของ kubectl, ชื่อของ controller, …) — สอง manager ที่เขียน field เดียวกันด้วยค่าที่ขัดกันคือ conflict จริงที่ถูก reject ไม่ใช่การเขียนทับแบบเงียบ ๆ | [kubectl & Declarative YAML](/kubernetes/th/foundations/kubectl-and-declarative-yaml/) |
| filter, score, bind (scheduling cycle) | pipeline ต่อ Pod หนึ่งตัวของ scheduler: **Filter** ตัด Node ที่รัน Pod นี้ไม่ได้เลยออกไป (`NodeResourcesFit`, `TaintToleration`, `PodTopologySpread`, … เหลือเป็นชุด Node ที่ *feasible*), **PostFilter** รัน `DefaultPreemption` ก็ต่อเมื่อไม่มี Node ไหน feasible เลย, **Score** จัดอันดับ Node ที่ feasible และ **Bind** ยืนยัน Pod เข้ากับ Node ที่ชนะ | [The Scheduler & Resource Requests](/kubernetes/th/scheduling-and-scaling/the-scheduler-and-resource-requests/) |
| Gateway API | ตัวสืบทอด Ingress ที่แสดงออกได้มากกว่าและแบ่งตาม role (`gateway.networking.k8s.io`) แยก object เดียวก้อนใหญ่ออกเป็น `GatewayClass` (ผู้ให้บริการ infrastructure), `Gateway` (instance ของ listener/load balancer) และ route type ต่าง ๆ (`HTTPRoute`, `GRPCRoute`, …) ที่ทีมต่างกันเป็นเจ้าของได้ | [Ingress & Gateway API](/kubernetes/th/networking/ingress-and-gateway-api/) |
| `Gateway` (resource) | object ของ Gateway API ที่ขอ infrastructure จัดการ traffic จริง ๆ (cloud load balancer, proxy ในคลัสเตอร์) จาก `GatewayClass` ที่ระบุชื่อไว้ ประกาศ listener ของมัน (protocol, port, hostname) — route ต่าง ๆ จะมาแนบกับมันทีหลัง | [Ingress & Gateway API](/kubernetes/th/networking/ingress-and-gateway-api/) |
| `GatewayClass` | object ของ Gateway API ที่ระบุชื่อ controller implementation (คล้ายกับ `IngressClass` หรือ `StorageClass`) ที่ `Gateway` อ้างถึงผ่าน `gatewayClassName` — เป็น cluster-scoped ปกติทีม platform ติดตั้งไว้ครั้งเดียว | [Ingress & Gateway API](/kubernetes/th/networking/ingress-and-gateway-api/) |
| GitOps | โมเดล deploy แบบ pull-based ที่ controller ซึ่งรันอยู่ *ข้างใน* คลัสเตอร์ (Argo CD, Flux) reconcile live state เข้ากับ manifest ใน Git repository อย่างต่อเนื่อง แทนที่จะให้ CI pipeline สั่ง `kubectl apply` จากข้างนอก — repository เองต่างหากที่เป็น source of truth ไม่ใช่การรัน pipeline ครั้งหนึ่ง | [GitOps & CI/CD for Kubernetes](/kubernetes/th/production-and-ecosystem/gitops-and-cicd-for-kubernetes/) |
| `GRPCRoute` | route type ของ Gateway API สำหรับ traffic แบบ gRPC (stable ที่ `gateway.networking.k8s.io/v1` เหมือนกับ `HTTPRoute`) match ตาม service/method ของ gRPC แทนที่จะเป็น path แบบ HTTP — ต้องการให้ listener ของ `Gateway` พูด HTTP/2 | [Ingress & Gateway API](/kubernetes/th/networking/ingress-and-gateway-api/) |

## H–I

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| headless Service | Service ที่สร้างด้วย `clusterIP: None` มันไม่ได้ virtual IP เลย และชื่อ DNS ของมัน resolve ตรงไปที่ IP ของ Pod แต่ละตัวข้างหลังมัน (หรือสำหรับ StatefulSet คือชื่อ DNS ต่อ Pod แบบคงที่หนึ่งชื่อ) แทนที่จะ load balance ผ่าน address เดียว — เป็นสิ่งที่ตัวตนของ StatefulSet ต้องพึ่งพา | [DNS & Service Discovery](/kubernetes/th/networking/dns-and-service-discovery/) |

| RBAC (Role / ClusterRole / RoleBinding / ClusterRoleBinding) | `Role`/`ClusterRole` ประกาศว่า *อนุญาตอะไร* (verb บน resource) ระดับ namespace หรือทั้งคลัสเตอร์ตามลำดับ; `RoleBinding`/`ClusterRoleBinding` ประกาศว่า *ใครได้สิทธิ์นั้น* ผูก Role/ClusterRole เข้ากับ user, group หรือ ServiceAccount — `ClusterRole` เองก็ผูกด้วย `RoleBinding` เพื่อจำกัดสิทธิ์ระดับคลัสเตอร์ให้เหลือแค่ namespace เดียวได้ด้วย | [RBAC & Service Accounts](/kubernetes/th/observability-and-security/rbac-and-service-accounts/) |
| reconcile / reconciliation loop | การกระทำหลักของ control loop: อ่าน desired state, อ่าน observed state แล้วยิง API call อะไรก็ตามที่ปิดช่องว่างระหว่างสองอย่างนี้ — ทำซ้ำต่อเนื่องตลอด ดังนั้นการแก้ field ที่ controller จัดการอยู่ด้วยมือจะถูกเขียนทับในรอบถัดไปเฉย ๆ | [What is Kubernetes?](/kubernetes/th/foundations/what-is-kubernetes/) |
| `ReferenceGrant` | object ของ Gateway API (`gateway.networking.k8s.io/v1beta1` ยังไม่ถูกเลื่อนเป็น v1) ที่อนุญาตการอ้างอิงข้าม namespace — เช่น `HTTPRoute` ใน namespace หนึ่งชี้ไปที่ Service ใน namespace อื่น — ต้องการการ opt-in ชัดเจนจาก namespace *เป้าหมาย* แทนที่จะเชื่อ object ที่อ้างอิงมาฝ่ายเดียว | [Ingress & Gateway API](/kubernetes/th/networking/ingress-and-gateway-api/) |
| Release (Helm) | instance หนึ่งที่ตั้งชื่อและถูกติดตามของ Chart ที่รันอยู่ในคลัสเตอร์ พร้อมประวัติ revision ของตัวเอง — `helm upgrade`/`helm rollback` ทำงานกับ resource ทั้งชุดที่ Release นั้นจัดการร่วมกัน ไม่ใช่ทีละ Deployment | [Helm Package Management](/kubernetes/th/production-and-ecosystem/helm-package-management/) |
| ReplicaSet | รักษาจำนวน Pod ที่ match selector (ตายตัว แก้ไม่ได้) ของมันให้เท่ากับ `replicas` อยู่ตลอดเวลา — แทบไม่เคยถูกสร้างตรง ๆ; Deployment สร้างและจัดการ ReplicaSet ให้เราเพื่อทำ rolling update ทับบน guarantee เรื่องจำนวนคงที่นี้ | [Deployments & ReplicaSets](/kubernetes/th/workloads/deployments-and-replicasets/) |
| requests / limits | `requests` คือพื้นที่ขั้นต่ำที่ scheduler จองไว้เทียบกับ Allocatable capacity ของ Node (และเป็นตัวเลขที่ QoS class ถูกคำนวณมาจาก); `limits` คือเพดานตอน runtime ที่ kubelet/cgroups บังคับใช้ — เกิน CPU limit จะถูก throttle, เกิน memory limit container จะถูก `OOMKilled` | [The Scheduler & Resource Requests](/kubernetes/th/scheduling-and-scaling/the-scheduler-and-resource-requests/) |
| ResourceQuota | เพดานแข็งระดับ namespace สำหรับการใช้ resource รวม (requests/limits ของ CPU/memory รวมกัน, จำนวน object) — ในขณะที่ `LimitRange` จำกัด Pod ทีละตัว `ResourceQuota` จำกัดทั้ง namespace พร้อมกัน | [Namespaces & Resource Quotas](/kubernetes/th/storage-and-config/namespaces-and-resource-quotas/) |

| scheduler (`kube-scheduler`) | component ของ control plane ที่เลือกว่า Pod ที่ยังไม่ผูกกับ Node ตัวไหนจะรันบน Node ไหน ผ่าน pipeline filter/score/bind — มันไม่รันอะไรเองเลย มันแค่เขียนการตัดสินใจ binding กลับไปที่ API server ให้ kubelet เอาไปทำต่อ | [The Scheduler & Resource Requests](/kubernetes/th/scheduling-and-scaling/the-scheduler-and-resource-requests/) |
| Secret | รูปร่างเหมือน ConfigMap เป๊ะ (ข้อมูล key/value ใช้เป็น env var หรือ mount เป็น volume) แต่ตั้งใจไว้สำหรับข้อมูลที่ sensitive — default เป็นการ encode แบบ base64 ไม่ใช่การ encrypt เลยไม่ได้เป็นความลับตอนอยู่นิ่ง ๆ เว้นแต่คลัสเตอร์จะตั้งค่า encryption-at-rest แยกไว้ | [ConfigMaps & Secrets](/kubernetes/th/storage-and-config/configmaps-and-secrets/) |

| selector | label query (`matchLabels`/`matchExpressions`) ที่เลือกกลุ่ม object แบบ dynamic — Service เลือก Pod ที่รองรับตัวเองด้วยวิธีนี้ และเป็นเหตุผลว่าทำไม Pod ที่มาแล้วไปไม่เคยต้องแก้ตัว Service เอง | [Services: ClusterIP, NodePort, LoadBalancer](/kubernetes/th/networking/services-clusterip-nodeport-loadbalancer/) |

| ServiceAccount | ตัวตนที่ Pod ใช้ authenticate กับ API server (ต่างจาก user ที่เป็นคน) — ทุก Pod รันในฐานะ ServiceAccount ตัวใดตัวหนึ่งเสมอ (`default` ถ้าไม่ได้ตั้งไว้) และ RBAC binding ที่ผูกกับมันต่างหากที่จำกัดว่า `kubectl`/client call ของ Pod นั้นเองทำอะไรได้บ้างจริง ๆ | [RBAC & Service Accounts](/kubernetes/th/observability-and-security/rbac-and-service-accounts/) |

| StatefulSet | จัดการ Pod ที่มีตัวตนคงที่และมีลำดับ (`<name>-0`, `<name>-1`, …) พร้อม PVC ต่อ Pod ที่คงที่ตามตัวตนนั้นไปแม้จะถูก reschedule — สิ่งที่ database หรืออะไรก็ตามที่ต้องการ "Pod เดิม ดิสก์เดิม" ทุกครั้งต้องการจริง ๆ ต่างจาก Deployment | [StatefulSets & DaemonSets](/kubernetes/th/workloads/statefulsets-and-daemonsets/) |
| `startupProbe` | รันก่อนที่ liveness/readiness probe จะเริ่มนับเลยด้วยซ้ำ ให้พื้นที่กับ container ที่ boot ช้าให้ boot จนเสร็จ — ควรตั้งขนาดให้ `failureThreshold * periodSeconds` ครอบคลุมเวลา boot ที่แย่ที่สุด ไม่งั้น liveness probe จะ restart container กลางคันตอน boot รีเซ็ตนาฬิกาใหม่ทุกครั้ง | [Probes: Liveness, Readiness & Startup](/kubernetes/th/observability-and-security/probes-liveness-readiness-startup/) |
| StorageClass | ระบุชื่อ provisioner (เกือบทุกครั้งเป็น CSI driver) พร้อม parameter สำหรับสร้าง PersistentVolume แบบ *dynamic* ตามความต้องการเมื่อ PVC อ้างถึงมัน — เป็นทางเลือกแทนการ provision PV เองล่วงหน้า และเป็นที่ตั้ง reclaim policy (`Delete` กับ `Retain`) | [PVs, PVCs & Storage Classes](/kubernetes/th/storage-and-config/persistent-volumes-claims-and-storage-classes/) |

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| taint / toleration | taint บน Node จะผลัก Pod ออกไป (`NoSchedule`, `PreferNoSchedule` หรือ `NoExecute` — ที่ evict Pod ที่รันอยู่แล้วด้วย เลือกได้ว่าหลัง `tolerationSeconds`); toleration ที่ match บน Pod ต่างหากที่ทำให้มันถูก schedule ที่นั่นได้ (หรืออยู่ต่อได้) — เป็นทิศตรงข้ามกับ affinity ที่ Pod ใช้ดึงตัวเองเข้าหา Node | [Node Affinity, Taints & Tolerations](/kubernetes/th/scheduling-and-scaling/node-affinity-taints-and-tolerations/) |

| `ValidatingAdmissionPolicy` | การ validate ในกระบวนการ admission แบบ in-process ด้วย CEL — stable ตั้งแต่ Kubernetes 1.30 — ประกาศว่าจะเช็คอะไรและเช็คยังไงตรง ๆ ใน object ของ policy เอง พร้อม object `...Binding` แยกต่างหากที่ให้ `paramRef`/`match` มาจำกัดขอบเขต ไม่ต้องมี validating webhook server เต็มรูปแบบสำหรับการเช็คทั่ว ๆ ไปหลายแบบ | [Pod & Cluster Security](/kubernetes/th/observability-and-security/pod-and-cluster-security/) |
