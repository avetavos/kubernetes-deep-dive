## The idea in one sentence

**Affinity** pulls a Pod toward certain Nodes (or other Pods), **`topologySpreadConstraints`** spreads a group of Pods evenly across a topology, and a **taint** repels Pods away from a Node unless the Pod carries a matching **toleration** — mechanisms that are often combined.

## nodeSelector and node affinity: matching on Node labels

The simplest way to constrain where a Pod runs is `nodeSelector` — an exact match against Node labels. If a Node does not have every label listed, it is not a candidate, full stop.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: gpu-inference
spec:
  nodeSelector:
    hardware: gpu
  containers:
    - name: inference
      image: inference-server:2.1.0
```

**Node affinity** does the same job with richer expressions (`In`, `NotIn`, `Exists`, and more) and, critically, a choice of how strictly the rule is enforced:

- **`requiredDuringSchedulingIgnoredDuringExecution`** — a hard requirement. If no Node satisfies it, the Pod stays Pending.
- **`preferredDuringSchedulingIgnoredDuringExecution`** — a soft preference with a `weight`. The scheduler favors matching Nodes but will still place the Pod elsewhere if it has to.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: gpu-inference-affinity
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: hardware
                operator: In
                values:
                  - gpu
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80
          preference:
            matchExpressions:
              - key: zone
                operator: In
                values:
                  - preferred
  containers:
    - name: inference
      image: inference-server:2.1.0
```

Both suffixes end in `IgnoredDuringExecution`, meaning that once a Pod is running, a later change to Node labels never causes it to be evicted — these rules only affect the initial scheduling decision. Proof that `preferred` actually steers placement without forcing it: labeling exactly one worker `zone=preferred` and creating a Pod with only that soft preference (no `nodeSelector`, no hard requirement) lands it on that worker every time, out of three otherwise-identical candidates:

```text
$ kubectl label node scheduling-worker2 zone=preferred
$ kubectl get pod prefers-zone -o wide
NAME           READY   STATUS    NODE
prefers-zone   1/1     Running   scheduling-worker2
```

## Pod affinity and anti-affinity: scheduling relative to other Pods, proven all-or-nothing

Node affinity looks at Node labels. **Pod affinity** and **pod anti-affinity** instead look at the labels of *other Pods already running*, using a `topologyKey` to define what "nearby" means (a hostname, a zone, and so on).

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-anti
spec:
  replicas: 4
  selector:
    matchLabels:
      app: web-anti
  template:
    metadata:
      labels:
        app: web-anti
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchExpressions:
                  - key: app
                    operator: In
                    values: ["web-anti"]
              topologyKey: kubernetes.io/hostname
      containers:
        - name: web
          image: registry.k8s.io/pause:3.10
```

This rule says "never put two `web-anti` Pods on the same host." On a 3-worker cluster, 3 replicas fit — one per Node — but the 4th has nowhere left to go, and `requiredDuringScheduling` is all-or-nothing: it stays genuinely `Pending`, not "somewhat spread":

```text
$ kubectl get pods -l app=web-anti -o wide
NAME                        READY   STATUS    NODE
web-anti-6476995565-5dwmp   1/1     Running   scheduling-worker
web-anti-6476995565-glvpv   0/1     Pending   <none>
web-anti-6476995565-l9tvf   1/1     Running   scheduling-worker2
web-anti-6476995565-rhltf   1/1     Running   scheduling-worker3

$ kubectl describe pod web-anti-6476995565-glvpv
Events:
  Warning  FailedScheduling  0/4 nodes are available: 1 node(s) had untolerated taint(s), 3 node(s) didn't match pod anti-affinity rules. preemption: 0/4 nodes are available: 1 Preemption is not helpful for scheduling, 3 No preemption victims found for incoming pod.
```

Compare that with `topologySpreadConstraints` below, which can express "spread evenly, allow up to N per Node" instead of this strict one-per-Node ceiling.

## `topologySpreadConstraints`: even distribution with a tunable skew

`topologySpreadConstraints` (`kubectl explain pod.spec.topologySpreadConstraints` on a live 1.37 cluster) spreads a group of Pods across a topology domain to within a tolerance, `maxSkew`, instead of anti-affinity's all-or-nothing rule:

```yaml
# k8s/node-affinity-taints-and-tolerations/topology-spread-deploy.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 6
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: DoNotSchedule
          nodeTaintsPolicy: Honor
          matchLabelKeys:
            - pod-template-hash
          labelSelector:
            matchLabels:
              app: web
      containers:
        - name: web
          image: registry.k8s.io/pause:3.10
```

- **`maxSkew`** — the maximum allowed difference between the most- and least-populated matching domain. `1` here means no Node may end up with 2 more matching Pods than any other.
- **`topologyKey: kubernetes.io/hostname`** — spread per-Node; use `topology.kubernetes.io/zone` to spread per-zone instead.
- **`whenUnsatisfiable`** — `DoNotSchedule` (hard, like `required` affinity) or `ScheduleAnyway` (soft, best-effort).
- **`matchLabelKeys: [pod-template-hash]`** — checked live: `kubectl explain pod.spec.topologySpreadConstraints.matchLabelKeys` on a real 1.37 API server reports **"This is a beta field ... requires the `MatchLabelKeysInPodTopologySpread` feature gate (enabled by default)"** — it is *not* GA yet, still beta since 1.27, contrary to an assumption that it would have graduated by 1.37. In practice it is on by default, so it behaves as if always available. It scopes skew-counting to Pods of the *same* ReplicaSet generation (see the rollout section below).

Proof of a clean 2-2-2 spread across 3 workers with 6 replicas:

```text
$ kubectl apply -f topology-spread-deploy.yaml
$ kubectl get pods -o wide
NAME                  READY   STATUS    NODE
web-b8b7dc6c7-4dpx9   1/1     Running   scheduling-worker
web-b8b7dc6c7-llb6c    1/1     Running   scheduling-worker
web-b8b7dc6c7-csj9b   1/1     Running   scheduling-worker2
web-b8b7dc6c7-l9qrl   1/1     Running   scheduling-worker2
web-b8b7dc6c7-hf4pl   1/1     Running   scheduling-worker3
web-b8b7dc6c7-nqxj9   1/1     Running   scheduling-worker3
```

### The `nodeTaintsPolicy` trap, proven

The same manifest **without** `nodeTaintsPolicy: Honor` gets 3 of 6 Pods permanently stuck `Pending` on this exact cluster:

```text
$ kubectl get pods -o wide
NAME                   READY   STATUS    NODE
web-57c75d6bbb-7m652   0/1     Pending   <none>
web-57c75d6bbb-gn7s7   0/1     Pending   <none>
web-57c75d6bbb-k67n4   1/1     Running   scheduling-worker3
web-57c75d6bbb-nwc64   1/1     Running   scheduling-worker
web-57c75d6bbb-xjl2m   0/1     Pending   <none>
web-57c75d6bbb-xz9lt   1/1     Running   scheduling-worker2

$ kubectl describe pod web-57c75d6bbb-7m652
Events:
  Warning  FailedScheduling  0/4 nodes are available: 1 node(s) had untolerated taint(s), 3 node(s) didn't match pod topology spread constraints.
```

`kubectl explain pod.spec.topologySpreadConstraints.nodeTaintsPolicy` spells out why: **"If this value is nil, the behavior is equivalent to the `Ignore` policy"** — meaning the tainted, unschedulable control-plane Node still counts as a valid topology domain with **0** matching Pods by default. With one Pod already on each of the 3 workers (1-1-1) and the control-plane counted as a 4th domain at 0, placing a 4th Pod anywhere would make the skew `2 - 0 = 2`, over the `maxSkew: 1` limit — so nothing after the first 3 Pods can schedule, cluster-wide, forever. Setting `nodeTaintsPolicy: Honor` excludes Nodes the incoming Pod cannot tolerate from the domain count, which is what fixed it above.

### `matchLabelKeys` during a rolling update, proven

Trigger a rolling update (`maxUnavailable: 0, maxSurge: 1`) on the spread Deployment **without** `matchLabelKeys` and watch a surge Pod land where 2 pods of the *previous* generation already sit, because the constraint counts every generation together:

```text
$ kubectl set image deploy/rollout-demo web=nginx:1.27.2-alpine
t+8s: rollout-demo-579bddcff9-2cpvt  Running  scheduling-worker  (old gen 579bddcff9)
t+8s: rollout-demo-579bddcff9-hmj2l  Running  scheduling-worker  (old gen 579bddcff9)
t+8s: rollout-demo-676f6cdd75-2bdwb  Running  scheduling-worker  (NEW gen 676f6cdd75)
```

`scheduling-worker` now genuinely holds 3 Pods (2 old + 1 new) for a moment — still within `maxSkew: 1` overall (3 vs 2 vs 2), but the new generation's *own* distribution is uneven purely by coincidence of where old Pods happened to be. Add `matchLabelKeys: [pod-template-hash]` and repeat the same rollout: the constraint now counts each generation's Pods separately, so the first surge Pod of a brand-new generation always starts its *own* domain count at 0 everywhere — regardless of where the outgoing generation's Pods are:

```text
$ kubectl patch deploy rollout-demo --type=json -p='[{"op":"add","path":"/spec/template/spec/topologySpreadConstraints/0/matchLabelKeys","value":["pod-template-hash"]}]'
$ kubectl set image deploy/rollout-demo web=nginx:1.27.3-alpine
t+1s: rollout-demo-548b8ff4cb-djfk9  ContainerCreating  scheduling-worker   (NEW gen 548b8ff4cb, 1st of its generation)
t+1s: rollout-demo-676f6cdd75-2bdwb  Running            scheduling-worker   (old gen 676f6cdd75)
t+1s: rollout-demo-7b5cbfbdb7-bdd57  Running            scheduling-worker   (old gen 7b5cbfbdb7)
```

`matchLabelKeys` merges `pod-template-hash: 548b8ff4cb` into the effective `labelSelector` for that surge Pod's own admission, so its skew calculation only ever sees Pods of the *same* hash — never blocked, and never artificially concentrated, by whichever Node the outgoing generation happens to occupy.

## Taints and tolerations: a Node repelling Pods

Affinity is a Pod deciding where it wants to go. A **taint** flips that around: it is applied to a **Node**, and it repels every Pod that does not carry a matching **toleration**.

```bash
# Taint a node so it repels ordinary Pods
kubectl taint nodes gpu-node-1 hardware=gpu:NoSchedule
```

Three taint effects, in increasing strength:

- **`NoSchedule`** — new Pods without a matching toleration will not be scheduled here. Pods already running are left alone.
- **`PreferNoSchedule`** — a soft version; the scheduler tries to avoid the Node but will use it if it has to.
- **`NoExecute`** — new Pods are blocked, *and* any already-running Pod on the Node that lacks a matching toleration is evicted.

A Pod opts in with a `tolerations` entry that matches the taint's key, value, and effect:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: gpu-inference-toleration
spec:
  tolerations:
    - key: hardware
      operator: Equal
      value: gpu
      effect: NoSchedule
  nodeSelector:
    hardware: gpu
  containers:
    - name: inference
      image: inference-server:2.1.0
```

A toleration only cancels out a taint — it does not attract the Pod there. That is why a dedicated GPU node pool is usually built from both mechanisms at once: the Nodes are tainted so ordinary Pods stay off them, and the GPU workload's Pods both tolerate that taint and use `nodeSelector` (or node affinity) to request scheduling there, along with a GPU resource request.

### `NoExecute` with `tolerationSeconds`, timed for real

`tolerationSeconds` lets a Pod tolerate a `NoExecute` taint, but only for a bounded grace period before it is evicted anyway — useful for "ride out a short node problem, but leave if it persists":

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: tolerates-briefly
spec:
  nodeSelector:
    kubernetes.io/hostname: scheduling-worker3
  tolerations:
    - key: dedicated
      operator: Equal
      value: batch
      effect: NoExecute
      tolerationSeconds: 10
  containers:
    - name: c
      image: registry.k8s.io/pause:3.10
```

```text
$ kubectl taint nodes scheduling-worker3 dedicated=batch:NoExecute
$ kubectl apply -f toleration-seconds-pod.yaml   # created 16:43:07, taint already present
16:43:07  Running
16:43:16  Running
16:43:18  Succeeded   (deletionTimestamp set)
16:43:19  Error from server (NotFound): pods "tolerates-briefly" not found
```

The Pod ran for roughly 10 seconds after the taint applied, then was evicted right on schedule — `tolerationSeconds` is a real, enforced clock, not a suggestion.

### Built-in `node.kubernetes.io/*` taints

Kubernetes applies several taints automatically, without any operator action — kind's control-plane Node carries one from the moment it is created:

```text
$ kubectl describe node scheduling-control-plane | grep Taints
Taints:             node-role.kubernetes.io/control-plane:NoSchedule
```

The most operationally important built-in taints are `node.kubernetes.io/not-ready` and `node.kubernetes.io/unreachable` (both `NoExecute`, applied by the node controller the moment a Node's `Ready` condition goes false or the node controller loses contact with it) and `node.kubernetes.io/unschedulable` (`NoSchedule`, mirrors `kubectl cordon`). Every Pod tolerates `not-ready`/`unreachable` for `300s` by default (via a default `tolerationSeconds` the API server adds automatically) — which is exactly the mechanism behind "a Pod survives a brief node blip but is evicted if the Node stays down."

## Mental Model

There are really only two directions in this lesson, and everything is one or the other. **Pulling**: `nodeSelector`, node affinity, pod affinity, and the preferred half of `topologySpreadConstraints` all describe what a Pod *wants* — a Node with a label, proximity to other Pods, an even spread — and a Pod that cannot get what it wants either stays `Pending` (`required`) or settles for second-best (`preferred`). **Pushing**: taints describe what a *Node* refuses, independent of any Pod's wishes, and only a matching toleration cancels that push — it never becomes a pull. `topologySpreadConstraints` sits in between: it counts Pods across a topology and its own `nodeTaintsPolicy` decides whether a taint (a push) also removes a Node from being counted as a spread target at all — proven above, getting that one field wrong silently changes "spread evenly" into "wedge forever."

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| `podAntiAffinity` `requiredDuringScheduling` | Absolute guarantee: never two matching Pods on one domain (proven above) | All-or-nothing — the (N+1)th replica stays Pending with no partial credit, proven above |
| `topologySpreadConstraints` with `maxSkew` | Tunable "spread evenly, allow up to N difference" instead of all-or-nothing | Needs `nodeTaintsPolicy: Honor` on any cluster with tainted/not-yet-Ready Nodes, or it can silently wedge (proven above) |
| `matchLabelKeys: [pod-template-hash]` on a spread constraint | Each rollout generation gets spread independently, not blocked or skewed by the outgoing generation (proven above) | Still a beta field (checked live: 1.37, enabled by default) — not yet a documented-stable guarantee |
| `preferredDuringScheduling` (node or pod affinity) | Never blocks scheduling; the Pod always lands somewhere | No guarantee at all under contention — proven above, a soft preference can be silently skipped |
| `tolerationSeconds` on a `NoExecute` toleration | Rides out a brief Node problem instead of an immediate evict | If set too long, a genuinely bad Node keeps the Pod past when it should have moved (proven above with a real timed eviction) |

## Common Misconceptions

- **"`topologySpreadConstraints` and `podAntiAffinity` are two syntaxes for the same guarantee."** Proven above: anti-affinity's `requiredDuringScheduling` is strictly one-per-domain (all-or-nothing), while spread's `maxSkew` allows a tunable difference and degrades gracefully with `ScheduleAnyway`.
- **"A tainted or not-yet-Ready control-plane Node just gets ignored by scheduling features automatically."** Proven above: without `nodeTaintsPolicy: Honor`, a tainted Node still counts as a topology domain with 0 Pods, which can make `maxSkew` impossible to satisfy anywhere, cluster-wide.
- **"`preferredDuringSchedulingIgnoredDuringExecution` will still evict a Pod if the preference stops being true later."** Both `required` and `preferred` end in `IgnoredDuringExecution` — proven in the API docs and by the fact that neither affinity type ever triggers an eviction on its own once a Pod is running.
- **"A toleration attracts a Pod to the tainted Node, the same way affinity does."** Proven above: a toleration only cancels a taint's *repulsion* — the Pod still needs a `nodeSelector` or affinity rule to actually be drawn there.
- **"`tolerationSeconds` is advisory, like a soft preference."** Proven above with real timestamps: the Pod is evicted right on schedule once the window elapses, not "eventually" or "if convenient."

## Reading AI-generated code

When reviewing a generated affinity, spread, or toleration block, check for:

- `topologySpreadConstraints` with no `nodeTaintsPolicy` set, on any cluster that has a control-plane or cordoned Node — proven above, this can silently wedge scheduling past the first N Pods (N = number of untainted Nodes) with no obvious error pointing at the real cause.
- `podAntiAffinity` `requiredDuringScheduling` used where the intent was really "spread evenly, but don't block on it" — proven above, `required` anti-affinity is all-or-nothing; `topologySpreadConstraints` with `whenUnsatisfiable: ScheduleAnyway` is the softer tool for that intent.
- A rolling-update Deployment with `topologySpreadConstraints` but no `matchLabelKeys: [pod-template-hash]` — proven above, without it the spread constraint mixes generations together during a rollout, which is rarely the intent.
- A `nodeSelector` or `tolerations` entry that references a label/taint key which no Node in the cluster actually has — this is a silent no-op: the toleration matches nothing, and the Pod schedules (or fails to) exactly as if it were absent, which is easy to mistake for "this is protecting against a taint" when it protects against nothing.
- `tolerationSeconds` set on a taint the Pod was never actually meant to ride out (e.g. copied from an unrelated example) — proven above, it is a real enforced timer, so a wrong value either evicts too eagerly or leaves a Pod on a bad Node far longer than intended.
- A GPU/dedicated-node toleration with no matching `nodeSelector`/affinity — the Pod merely stops being repelled, it is not drawn to the tainted Nodes, so it can land anywhere else in the cluster just as easily.

<Callout title="The one-line takeaway">
**Node affinity** pulls a Pod toward Nodes, hard with **`requiredDuringSchedulingIgnoredDuringExecution`** or soft with **`preferredDuringSchedulingIgnoredDuringExecution`** (proven above, a soft preference reliably steers placement without blocking); **pod affinity/anti-affinity** does the same relative to other Pods, but `required` anti-affinity is strictly all-or-nothing (proven above, replica 4 of 4 stuck Pending on 3 Nodes). **`topologySpreadConstraints`** is the tunable alternative — `maxSkew`/`topologyKey`/`whenUnsatisfiable` — but its still-beta **`matchLabelKeys`** matters during rollouts (proven above, it keeps each generation's spread independent) and its **`nodeTaintsPolicy`** defaults to counting tainted Nodes as empty domains, which can silently wedge scheduling cluster-wide (proven above) unless set to **`Honor`**. A **taint** on a Node works the opposite direction — it **repels** Pods unless they carry a matching **toleration**, with effects **`NoSchedule`**, **`PreferNoSchedule`**, and **`NoExecute`** (which evicts running Pods on a real, enforced **`tolerationSeconds`** clock, proven above) — plus built-in `node.kubernetes.io/*` taints the cluster applies automatically.
</Callout>
