## The idea in one sentence

Kubernetes gives you just enough logging, live debugging, and metrics out of the box to investigate a single Pod right now, but nothing that aggregates or retains data across the cluster — that is a separate stack you have to add yourself.

## kubectl logs: a live window, not a history book

`kubectl logs` reads a container's stdout/stderr directly from the node it is running on. It is the fastest way to look at what a Pod is doing right this moment:

```bash
# Stream logs live as they are written
kubectl logs -f deploy/checkout

# A Pod with more than one container: pick which one
kubectl logs my-pod -c sidecar

# The container just crashed and restarted: see its last words before it died
kubectl logs my-pod --previous
```

`--previous` is the one people forget about and then need most: when a container crash-loops, the *current* container's logs may already be past the interesting part, but `--previous` shows you the logs from the instance that just crashed. Proof, a container that prints one line and exits with a non-zero code:

```yaml
# k8s/logging-and-metrics/crasher.yaml
apiVersion: v1
kind: Pod
metadata:
  name: crasher
  namespace: log-demo
spec:
  restartPolicy: Always
  containers:
    - name: c
      image: busybox
      command: ["sh", "-c", "echo 'boot message, crashing now'; sleep 2; exit 1"]
```

```text
$ kubectl get pod crasher
NAME      READY   STATUS   RESTARTS   AGE
crasher   0/1     Error    1 (2s ago) 12s

$ kubectl logs crasher --previous
boot message, crashing now
```

The kubelet only keeps a limited number of terminated containers around before garbage-collecting their logs, so `--previous` has to be run reasonably soon after the crash — wait too long through several more restart cycles and even `--previous` reports `unable to retrieve container logs`, because the specific terminated container instance it would have read from is already gone.

Selecting logs across many Pods at once, and trimming what you fetch:

```text
$ kubectl logs -l app=web -n log-demo --tail=2 --prefix
[pod/web-57787d5f95-dwbnf/c] tick 2 from web-57787d5f95-dwbnf
[pod/web-57787d5f95-dwbnf/c] tick 3 from web-57787d5f95-dwbnf
[pod/web-57787d5f95-g6qrh/c] tick 2 from web-57787d5f95-g6qrh
[pod/web-57787d5f95-g6qrh/c] tick 3 from web-57787d5f95-g6qrh
[pod/web-57787d5f95-q9hkw/c] tick 1 from web-57787d5f95-q9hkw
[pod/web-57787d5f95-q9hkw/c] tick 2 from web-57787d5f95-q9hkw

$ kubectl logs -l app=web -n log-demo --since=5s --prefix
[pod/web-57787d5f95-g6qrh/c] tick 2 from web-57787d5f95-g6qrh
[pod/web-57787d5f95-g6qrh/c] tick 3 from web-57787d5f95-g6qrh
[pod/web-57787d5f95-q9hkw/c] tick 2 from web-57787d5f95-q9hkw
[pod/web-57787d5f95-dwbnf/c] tick 2 from web-57787d5f95-dwbnf
[pod/web-57787d5f95-dwbnf/c] tick 3 from web-57787d5f95-dwbnf
```

`-l` (a label selector) plus `-f` streams every matching Pod at once, each line tagged with `--prefix` so you know which Pod it came from — the built-in equivalent of what a third-party tool like `stern` gives you with nicer coloring and cross-namespace selectors, for the common case of "tail everything matching this label right now."

The important limitation: Kubernetes itself does **not** aggregate or persist these logs. If a Pod is deleted, its logs typically go with it. There is no built-in "search logs across every Pod in the cluster." That job belongs to a separate logging stack — commonly a node-level agent such as **Fluent Bit** (or Fluentd/Vector) that tails every container's log files and ships them to a backend like **Loki** or **Elasticsearch**, where they can be searched and retained long-term.

```yaml
# A minimal illustration: Fluent Bit runs as a DaemonSet so one agent per node
# tails every container's logs and forwards them to a backend
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluent-bit
spec:
  selector:
    matchLabels:
      app: fluent-bit
  template:
    metadata:
      labels:
        app: fluent-bit
    spec:
      containers:
        - name: fluent-bit
          image: fluent/fluent-bit:5.1
          volumeMounts:
            - name: varlog
              mountPath: /var/log
      volumes:
        - name: varlog
          hostPath:
            path: /var/log
```

## `kubectl exec` doesn't always work — ephemeral containers and `kubectl debug`

A minimal or **distroless** image (built `FROM scratch` or `gcr.io/distroless/static`, or a utility image like `registry.k8s.io/pause`) ships no shell and no coreutils at all — it is just the one static binary the container runs. `kubectl exec` needs *something* to run inside the container, so it fails with a real, specific error, not a Kubernetes-level permission problem:

```text
$ kubectl exec distroless-app -n log-demo -- sh
error: Internal error occurred: Internal error occurred: error executing command in container: failed to exec in container: failed to start exec "28673a297...": OCI runtime exec failed: exec failed: unable to start container process: exec: "sh": executable file not found in $PATH
```

**Ephemeral containers** (GA/stable since Kubernetes **1.25**) solve this: `kubectl debug` attaches a brand-new, throwaway container to an *already-running* Pod, sharing the target's process namespace, without restarting or replacing anything already in the Pod spec:

```text
$ kubectl debug -it distroless-app -n log-demo --image=busybox --target=app -- ps aux
Targeting container "app". If you don't see processes from this container it may be because the container runtime doesn't support this feature.
Defaulting debug container name to debugger-988qv.
PID   USER     TIME  COMMAND
    1 65535     0:00 /pause
   17 root      0:00 ps aux
```

`--target=app` is what makes this useful rather than just "a busybox Pod next to mine": the ephemeral container shares the **process namespace** of the named target container, so `ps aux` run *inside the debug container* sees PID 1 as `/pause` — the distroless target's own process — not just its own shell. Nothing about the original Pod spec changed; `kubectl get pod distroless-app -o yaml` still shows only the one original container plus a new `ephemeralContainers` entry.

`kubectl debug` also reaches a whole **Node**, when the problem is with the node itself rather than one Pod on it — it schedules a privileged debug Pod that mounts the node's root filesystem at `/host`:

```text
$ kubectl debug node/observability-worker -it --image=busybox -- chroot /host cat /etc/os-release
VERSION_ID="13"
VERSION="13 (trixie)"
ID=debian
```

## Events as a signal, not just a side note

Every Warning event (`FailedScheduling`, `BackOff`, `Unhealthy`, and more) is queryable directly, filtered server-side:

```text
$ kubectl get events -n log-demo --field-selector type=Warning --sort-by=.lastTimestamp
LAST SEEN   TYPE      REASON    OBJECT        MESSAGE
37s         Warning   BackOff   pod/crasher   Back-off restarting failed container c in pod crasher_log-demo(607c53af-...)
3s          Warning   BackOff   pod/crasher   Back-off restarting failed container c in pod crasher_log-demo(91d78655-...)

$ kubectl get events -n log-demo --field-selector involvedObject.name=crasher
LAST SEEN   TYPE     REASON      OBJECT        MESSAGE
31s         Normal   Scheduled   pod/crasher   Successfully assigned log-demo/crasher to observability-worker
29s         Normal   Pulled      pod/crasher   Successfully pulled image "busybox" in 1.59s ...
5s          Normal   Started     pod/crasher   Container started
3s          Warning  BackOff     pod/crasher   Back-off restarting failed container c in pod crasher_log-demo(...)
```

`--field-selector` narrows to exactly one object or one event type server-side (cheaper than piping through `grep`), and `kubectl get events --watch` streams new events live as the API server emits them — the same watch mechanism the rest of `kubectl`'s `-w`/`--watch` flags use. Events are also short-lived (the default retention is about an hour, `--event-ttl` on the API server), so they answer "what just happened" far better than "what happened yesterday" — another reason a real logging/metrics stack exists.

## metrics-server: enough for kubectl top and autoscaling, nothing more

**metrics-server** is a lightweight cluster add-on that collects CPU and memory usage from every kubelet and holds it **in memory only** — no history, no persistence, no alerting. It is not part of kind by default and needs one real patch to tolerate kind's self-signed kubelet certificates:

```bash
# scripts/install-metrics-server.sh
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
kubectl -n kube-system patch deployment metrics-server --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
kubectl -n kube-system rollout status deploy/metrics-server
```

It exists to power exactly two things, proven with real numbers from a live 1.37 kind cluster:

```text
$ kubectl top nodes
NAME                          CPU(cores)   CPU(%)   MEMORY(bytes)   MEMORY(%)
observability-control-plane   166m         1%       806Mi           9%
observability-worker          41m          0%       222Mi           2%
observability-worker2         43m          0%       244Mi           2%

$ kubectl top pods -n log-demo
NAME                   CPU(cores)   MEMORY(bytes)
distroless-app         0m           0Mi
web-57787d5f95-dwbnf   1m           0Mi
web-57787d5f95-g6qrh   1m           0Mi
web-57787d5f95-q9hkw   1m           0Mi
```

...and the **HorizontalPodAutoscaler**, which polls metrics-server to decide whether to scale a Deployment up or down (covered in depth in the Scheduling and Scaling module):

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: checkout
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: checkout
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

metrics-server is explicitly **not** a monitoring solution — if you ask "what was CPU usage three hours ago" or "alert me when memory crosses 90%", metrics-server has no answer. It only knows the current snapshot.

## Prometheus + Grafana: the de facto observability stack

For real observability — historical data, dashboards, alerting — the standard combination is **Prometheus** and **Grafana**.

Prometheus works by **scraping**: it periodically pulls metrics from an HTTP `/metrics` endpoint that a workload exposes in Prometheus's own text format. Many applications and sidecars expose this endpoint themselves; for cluster-level object state (Deployment replica counts, Pod phases, node conditions, and so on) Prometheus scrapes **kube-state-metrics**, a separate service that turns Kubernetes API objects into Prometheus metrics.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: checkout
  annotations:
    prometheus.io/scrape: "true"
    prometheus.io/port: "9090"
spec:
  containers:
    - name: checkout
      image: checkout:2.3.0
      ports:
        - containerPort: 9090
```

```bash
# A workload's own /metrics endpoint, in Prometheus text format
curl http://checkout-pod:9090/metrics
```

Prometheus stores this scraped data as a time series and evaluates alerting rules against it. **Grafana** then sits on top as the visualization layer, querying Prometheus to render dashboards — CPU/memory trends, request latency, error rates — and to drive alert notifications.

## OpenTelemetry Collector: a vendor-neutral pipeline, not a Prometheus replacement

The **[OpenTelemetry Collector](https://opentelemetry.io/docs/collector/)** is a vendor-agnostic pipeline that can receive, process, and export **logs, metrics, and traces** together, rather than requiring a separate agent per signal per vendor. In a Kubernetes cluster it typically runs as a DaemonSet (node-level collection, similar in shape to Fluent Bit above) or a sidecar, taking data in from applications and routing it to one or more backends — batching, retrying, and filtering along the way.

Critically, the Collector **complements** Prometheus rather than replacing it: it can *receive* metrics in Prometheus's own scrape format and re-export them onward, letting a cluster standardize on one collection pipeline while still choosing (or changing) backends — Prometheus, a commercial APM vendor, or both — without re-instrumenting every application. This lesson covers it as an overview only; it is not installed here.

## Mental Model

Everything in this lesson is Kubernetes giving you a *live window*, never a *history*. `kubectl logs`/`exec`/`debug`/`top`/`get events` all answer "what is true about this Pod or Node right now (or very recently)" — and every one of them loses its data the moment the Pod is deleted, the container is garbage-collected, or the event TTL expires. Real observability (Fluent Bit → Loki/Elasticsearch, Prometheus → Grafana, or an OpenTelemetry Collector pipeline feeding either) exists specifically to survive that — it copies the live signal out to somewhere with retention *before* Kubernetes discards it. Ephemeral containers fit the same story from a different angle: a distroless image intentionally has no live-window tooling built in at all, so `kubectl debug` brings its own temporary window rather than assuming one already exists inside the container.

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| `kubectl logs`/`exec`/`debug`/`top` | Zero extra components, works the moment the cluster exists (proven above) | No retention, no history, no aggregation across Pods or time |
| `kubectl debug --target` (ephemeral containers) | Debug a distroless/minimal container without rebuilding its image or restarting the Pod (proven above) | Requires the container runtime to support ephemeral containers/shared process namespaces; adds a visible extra container to the Pod while it runs |
| Fluent Bit + Loki/Elasticsearch | Searchable, retained logs across every Pod and past deletions | Real infrastructure to run, size, and keep available |
| metrics-server | Minimal footprint, exactly enough for `kubectl top`/HPA (proven above) | No history at all — cannot answer "what was it an hour ago" |
| Prometheus + Grafana | Historical, queryable, alertable — the de facto standard | Another stateful service to operate (storage, retention, scrape config) |
| OpenTelemetry Collector | One pipeline for logs+metrics+traces, vendor-neutral, can front Prometheus | Yet another moving part; does not remove the need for a backend (Prometheus, Loki, or a vendor) to actually store the data |

## Common Misconceptions

- **"`kubectl exec` should always work to get a shell in any container."** Proven above with a real, specific error: a distroless/minimal image has no shell binary at all, so `exec` fails with `executable file not found in $PATH` — the fix is `kubectl debug --target`, not assuming the container is broken.
- **"Kubernetes stores logs somewhere durable by default."** Proven above: logs are read live from the node, and after enough restart cycles even `kubectl logs --previous` can no longer retrieve a terminated container's log — nothing is durable without a separate logging stack.
- **"metrics-server is a lightweight Prometheus."** Proven above: it holds only the current snapshot, in memory, with zero history — it exists purely to answer `kubectl top` and feed the HPA, not to be queried or alerted on.
- **"`kubectl debug --target` restarts or replaces the Pod's container."** Proven above: the original container (`/pause`, PID 1) kept running throughout; the ephemeral container is a separate, additional process visible in the same `ps aux` output, not a replacement.
- **"OpenTelemetry Collector replaces Prometheus."** Per the OpenTelemetry docs, the Collector is a vendor-neutral pipeline that can *receive from and export to* Prometheus, among other backends — it is a routing/processing layer, not a storage backend that competes with Prometheus.

## Reading AI-generated code

When reviewing generated debugging instructions, log-viewing commands, or observability manifests, check for:

- `kubectl exec -it <pod> -- /bin/sh` suggested as the first debugging step against a distroless or `FROM scratch` image — proven above, this fails immediately with a real "executable file not found" error; the correct tool is `kubectl debug --target`.
- `kubectl logs <pod>` (no `--previous`) suggested to diagnose *why* a container just crashed — if the container already restarted, the current logs may start after the crash; `--previous` is what shows the dying instance's last output, proven above.
- A troubleshooting doc that assumes logs are searchable across the whole cluster or across time out of the box — proven above, Kubernetes itself keeps no history at all; that capability only exists once a logging stack (Fluent Bit/Loki, etc.) is actually deployed.
- `metrics-server` proposed as a substitute for "we need monitoring/alerting" — proven above, it has no history and cannot alert; that requires Prometheus (or an equivalent) plus Grafana or another alerting layer.
- A `hostPath: /var/log` mount suggested as a quick way to "collect logs" from inside an application Pod itself, instead of a dedicated node-level DaemonSet agent — this couples the application to node-local paths and misses every other Pod's logs on that node; the standard pattern here is a DaemonSet like Fluent Bit, not per-application log collection code.
