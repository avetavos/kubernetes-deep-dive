## The idea in one sentence

A **Pod** is the smallest deployable unit in Kubernetes — one or more containers that always run together on the same node, sharing one network namespace and, optionally, one or more volumes.

## What containers in a Pod share

Every container in a Pod gets the same **IP address** and the same **network namespace**. That means two containers in one Pod reach each other over `localhost`, on whatever port the other one is listening on — no cluster networking involved. Containers in a Pod can also mount the same **volume**, which is how a sidecar reads files that the main container writes.

```bash
# From inside the "app" container, a sidecar in the same Pod is reachable on localhost
kubectl exec -it app-with-sidecar -c app -- curl -s http://localhost:9090/metrics
```

This shared-namespace guarantee is the whole reason a Pod exists as a concept: it is the boundary within which "these containers are always co-located and can talk over localhost" holds true. Containers in different Pods never get this for free — they need a Service and a routable address.

## Multi-container patterns: sidecars and init containers

Two patterns cover almost every reason to put more than one container in a Pod:

- **Sidecar** — a helper container that runs alongside the main container for the Pod's whole lifetime, for example a log shipper that tails the main container's log files and forwards them, or a proxy that handles TLS termination.
- **Init containers** — containers that run **to completion, in order, before any main container starts**. A common use is waiting for a dependency to become reachable, or running a one-time migration before the main container boots.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-sidecar
spec:
  restartPolicy: Always
  initContainers:
    - name: wait-for-db
      image: busybox:1.38
      command: ['sh', '-c', 'until nc -z db 5432; do sleep 1; done']
    - name: log-shipper
      image: myregistry/log-shipper:2.1.0
      restartPolicy: Always
      volumeMounts:
        - name: logs
          mountPath: /var/log/app
  containers:
    - name: app
      image: myregistry/app:1.4.0
      ports:
        - containerPort: 8080
      volumeMounts:
        - name: logs
          mountPath: /var/log/app
  volumes:
    - name: logs
      emptyDir: {}
```

`wait-for-db` blocks the Pod's startup until the database is reachable, then exits successfully; only then do the rest of the `initContainers` and the main `containers` start, in order. Notice that `log-shipper` also lives under `initContainers`, not `containers` — but it sets `restartPolicy: Always` on itself. That single field is what makes it a **native sidecar** instead of a regular init container: kubelet starts it (and keeps restarting it if it exits) before `app` starts, and on Pod termination it stops `app` first and this sidecar last, so a log shipper draining the final lines of output is not killed out from under the container it is shipping logs for. This has been a **stable, GA feature since Kubernetes v1.33** (first available in v1.28) — before it existed, the only way to run a sidecar was as an ordinary entry in `containers`, which has none of these startup- or shutdown-ordering guarantees relative to the main container. `app` and `log-shipper` share the Pod's network namespace and the `logs` volume, which is how `log-shipper` can read the files `app` writes.

## Pod lifecycle: phases, states, and restartPolicy

A Pod moves through a small set of **phases**: `Pending` (accepted but not all containers are running yet, often waiting on scheduling or image pulls), `Running` (bound to a node, at least one container running), `Succeeded` or `Failed` (all containers have terminated), and occasionally `Unknown` (the Pod's state cannot be obtained). Underneath the phase, each individual container has its own **state**: `Waiting`, `Running`, or `Terminated`.

What happens when a container exits is controlled by `restartPolicy` on the Pod spec: `Always` restarts any exited container forever (the default, used for long-running services), `OnFailure` restarts only on a non-zero exit code (used for Jobs), and `Never` never restarts (also common for Jobs, or for one-shot debugging Pods).

```bash
# Watch a Pod move through its phases
kubectl get pod app-with-sidecar --watch

# Container-level detail: state (Waiting/Running/Terminated), restart count, exit code
kubectl describe pod app-with-sidecar
```

## Pod termination lifecycle: SIGTERM, grace period, and preStop

`kubectl delete pod` does not kill a Pod's containers directly. It sets `metadata.deletionTimestamp` and then, **in parallel**, two things start:

1. The endpoint controller starts removing the Pod from every Service's `Endpoints`/`EndpointSlice` it backs.
2. The kubelet runs the container's `preStop` hook (if one is defined), then sends **SIGTERM** to PID 1 of each container, then waits — and if the container still hasn't exited once the **whole** `terminationGracePeriodSeconds` budget (which the `preStop` hook's own running time counts against) has elapsed, the kubelet sends **SIGKILL**.

```text
$ kubectl explain pod.spec.terminationGracePeriodSeconds
KIND:       Pod
VERSION:    v1

FIELD: terminationGracePeriodSeconds <integer>

DESCRIPTION:
    Optional duration in seconds the pod needs to terminate gracefully. May be
    decreased in delete request. Value must be non-negative integer. The value
    zero indicates stop immediately via the kill signal (no opportunity to shut
    down). If this value is nil, the default grace period will be used instead.
    The grace period is the duration in seconds after the processes running in
    the pod are sent a termination signal and the time when the processes are
    forcibly halted with a kill signal. Set this value longer than the expected
    cleanup time for your process. Defaults to 30 seconds.
```

### Proof: the race between endpoint removal and preStop, real timestamps

A `Pod` (`terminationGracePeriodSeconds: 15`) traps `SIGTERM` and, on receipt, sleeps 15s before exiting; its `preStop` hook sleeps 5s. It sits behind a headless-free `ClusterIP` Service. Deleting it while polling the backing `EndpointSlice` every 300ms and streaming the container's own timestamped log gives this real timeline (container log in UTC, endpoint poll in local time UTC+7 — only the deltas matter):

```text
# container log (kubectl logs -f term-demo --timestamps)
2026-09-26T07:50:24.632391178Z main started
2026-09-26T07:50:32.496035750Z preStop start
2026-09-26T07:50:37.500057586Z preStop end
2026-09-26T07:50:37.649504711Z SIGTERM received, sleeping 15s before exit
# (never logged: "main exiting now" -- SIGKILL cut it off, see below)
```

```text
# endpoint poll (kubectl get endpointslice -l kubernetes.io/service-name=term-demo, every 300ms)
14:50:31.946884000 ready=true  addrs=[10.244.2.2]
14:50:32.428941000 DELETE ISSUED
14:50:32.424496000 ready=true  addrs=[10.244.2.2]   # still true -- preStop hasn't even started yet
14:50:32.902948000 ready=false addrs=[10.244.2.2]   # <-- endpoint marked not-ready ~0.47s after delete
...(unchanged ready=false for the next ~15s)...
14:50:47.575059000 ready=false addrs=[]             # <-- endpoint entry fully removed
14:50:47.925334000 DELETE RETURNED
```

```text
# kubectl get events --field-selector involvedObject.name=term-demo
LAST SEEN   REASON    MESSAGE
0s          Killing   Stopping container main
```

Reading the two logs side by side: the `Endpoints`/`EndpointSlice` entry goes **not-ready within half a second of `kubectl delete`** — well before the 5-second `preStop` hook even finishes (`07:50:37.500`), let alone before `SIGTERM` is sent (`07:50:37.649`). This is *the* race the spec warns about: **readiness removal is not sequenced after preStop, it happens concurrently with it.** A client that keeps sending traffic based on a cached endpoint list (a client-side load balancer, an in-cluster proxy that didn't yet notice the update) can still hit the Pod for the whole `preStop` window — which is exactly the problem `preStop: sleep N` is for: it buys the time a real Service/kube-proxy/Ingress dataplane update needs to fully propagate before the container actually stops accepting new connections, **not** a guarantee that no traffic arrives during it.

The full picture: `preStop` ran for its 5s, `SIGTERM` landed at `07:50:37.649`, and the container's trap handler asked for 15 more seconds to exit gracefully — but the Pod was fully gone by `14:50:47.925`, only **~15.1s after the delete was issued**, not the ~20s the container asked for (5s preStop + 15s graceful exit). The container's `"main exiting now"` line **never appears in the log** — it was `SIGKILL`ed mid-sleep. That is `terminationGracePeriodSeconds: 15` doing exactly what it says: the budget is consumed from the moment `kubectl delete` is issued, `preStop`'s own 5s comes **out of** that same 15s, leaving only ~10s after `SIGTERM` for the container to actually exit.

### `terminationGracePeriodSeconds: 0` is dangerous

Setting it to `0` does not give the container a fast, clean shutdown — it skips almost the entire sequence above. Same Pod, `terminationGracePeriodSeconds: 0`:

```text
$ kubectl apply --dry-run=server -f term-demo-zero.yaml
pod/term-demo-zero created (server dry run)     # the API server accepts it -- no validation rejects grace period 0
```

```text
# container log
2026-09-26T07:51:15.005753381Z main started
2026-09-26T07:51:16.088548048Z preStop ran       # preStop *started* and logged its first line...
# ...and nothing else. No "SIGTERM received" line was ever logged.
```

```text
$ time kubectl delete pod term-demo-zero
pod "term-demo-zero" deleted
# real  0m0.055s
```

```text
# kubectl get events --field-selector involvedObject.name=term-demo-zero
LAST SEEN   REASON              MESSAGE
3s          Killing             Stopping container main
0s          FailedPreStopHook   PreStopHook failed
```

The delete call returned in **55 milliseconds**. The `preStop` hook was started, logged its first line, and was then killed mid-execution before its own `sleep 5` finished — the real, exact kubelet event is `FailedPreStopHook: PreStopHook failed`. The container's own `SIGTERM` trap handler never ran at all: there was no grace period left in which to deliver it and wait, so the kubelet went straight to `SIGKILL`. `terminationGracePeriodSeconds: 0` is for a Pod you are certain holds no state and needs no cleanup at all (some debug/test workloads) — it is never the right fix for "my rollout/delete is too slow," because it also throws away in-flight request draining, log flushing, and the endpoint-removal grace window discussed above.

### Native sidecars stop last, proven

Extending the `wait-for-db` / `log-shipper` example from earlier: on Pod deletion, kubelet stops ordinary containers (`main`) **first**, sends `SIGTERM` to the native sidecar (`initContainers` entry with `restartPolicy: Always`) only **after** every main container has exited, and only then starts counting down toward `SIGKILL`-ing the sidecar too. Proof, `terminationGracePeriodSeconds: 10`, `main` sleeps 2s after `SIGTERM` before exiting, sidecar just traps and exits immediately:

```text
# container "main"
2026-09-26T07:51:35.310165627Z [main] started
2026-09-26T07:51:37.315952878Z [main] SIGTERM received, sleeping 2s
2026-09-26T07:51:39.320772795Z [main] exiting

# container "log-shipper" (native sidecar, initContainers + restartPolicy: Always)
2026-09-26T07:51:35.245861918Z [sidecar] started
2026-09-26T07:51:40.267421296Z [sidecar] SIGTERM received, exiting
```

```text
$ kubectl get events --field-selector involvedObject.name=term-demo-sidecar
LAST SEEN   REASON    MESSAGE
Killing     Stopping container log-shipper
Killing     Stopping container main
```

`main` receives `SIGTERM` at `07:51:37.315` and finishes exiting at `07:51:39.320`; `log-shipper` does not receive its own `SIGTERM` until `07:51:40.267` — **after** `main` was already fully gone. This is the mechanism behind the "log shipper drains the final lines" guarantee from earlier: the sidecar is deliberately the last thing standing.

## Why bare Pods are not how you run things

A Pod is ephemeral by design and it is rarely something you create directly. If you `kubectl apply` a bare Pod and its node fails, or the container inside it crashes past what `restartPolicy` will fix, **nothing recreates that Pod** — it is simply gone. In practice you almost always create a Deployment, StatefulSet, or DaemonSet instead: those controllers own a Pod template, watch the actual state of the cluster, and recreate Pods whenever reality drifts from the desired count. The rest of this module is those controllers.

## Reading AI-generated code

When reviewing a generated Pod spec (or one embedded in a Deployment/StatefulSet/DaemonSet template), check for:

- Does it set `terminationGracePeriodSeconds: 0` "to make deletes faster" — proven above, this skips the `preStop` hook mid-execution (`FailedPreStopHook`) and never delivers `SIGTERM` at all, it does not make shutdown safer or cleaner.
- Does a container behind a Service have **no `preStop`** at all — proven above, the Service's `EndpointSlice` entry goes not-ready within ~0.5s of `kubectl delete`, but without a `preStop` sleep there's nothing bridging the gap while that removal propagates through kube-proxy/Ingress/mesh dataplanes.
- Is `terminationGracePeriodSeconds` set lower than the time the app's own shutdown code needs (flushing buffers, draining connections, closing DB pools) — the container gets `SIGKILL`ed mid-shutdown, proven above with the main container's own 15s exit sleep getting cut off at ~10s.
- Is a `restartPolicy: Always` "sidecar" written as a plain entry under `containers:` instead of `initContainers:` with `restartPolicy: Always` — that's just an ordinary container with no startup/shutdown ordering guarantee relative to the main container at all, not a native sidecar.
- Does the Pod assume `restartPolicy: Always` restarts a container that exited `0` — it does; `Always` restarts on *any* exit, success or failure, which is correct for long-running services but is a common source of confusion when someone expects "only restart on crash."

## Mental Model

A Pod's shutdown is not "kill the process," it is a **negotiated handoff with a deadline**: the cluster starts removing the Pod from service discovery and running your cleanup code at the same moment, and it will forcibly end the process once the clock you set (`terminationGracePeriodSeconds`) runs out — no matter how far your own cleanup got. `preStop` and your app's own `SIGTERM` handler are not two independent phases with their own budgets; they share **one** budget, counted from the instant `kubectl delete` runs. A native sidecar's ordering guarantee — starts first, stops last — exists specifically so that a support container (log shipper, proxy) never gets pulled out from under the thing it's supporting.

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Longer `terminationGracePeriodSeconds` | App gets real time to drain connections/flush data (proven above: cut short at the default budget, the app's own 15s exit sleep never completed) | Slower `kubectl delete`/rollouts; a genuinely hung container takes longer to be forcibly removed |
| `preStop: sleep N` | Bridges the real gap between "Pod marked for deletion" and "every dataplane component stopped routing to it" (proven above: endpoints go not-ready in ~0.5s, well before a 5s preStop even finishes) | Adds N seconds to every single Pod termination, whether or not there was in-flight traffic to drain |
| `terminationGracePeriodSeconds: 0` | Fractions of a second to fully remove a Pod (proven above: 55ms) | No `preStop` completion, no `SIGTERM` delivery, no graceful shutdown at all — proven above with a real `FailedPreStopHook` event |
| Native sidecar (`initContainers` + `restartPolicy: Always`) | Guaranteed last-to-stop ordering (proven above) for log shippers/proxies that must outlive the main container | One more container's resource footprint and one more thing to keep healthy for the Pod's whole life |

## Common Misconceptions

- **"`preStop` and the app's `SIGTERM` handler each get the full `terminationGracePeriodSeconds`."** Proven above: they share one budget. A 5s `preStop` against a 15s grace period leaves only ~10s for the app's own graceful shutdown after `SIGTERM`.
- **"The Pod stops receiving traffic only once the container actually exits."** Proven above: the `EndpointSlice` entry went not-ready ~0.5s after `kubectl delete`, many seconds before the container received `SIGTERM` at all — readiness removal races ahead of the container lifecycle, it doesn't wait for it.
- **"`terminationGracePeriodSeconds: 0` just skips the wait, the shutdown steps still run, just fast."** Proven above with a real `FailedPreStopHook` event: the `preStop` hook is killed mid-execution and `SIGTERM` is never delivered at all — it is not a fast graceful shutdown, it is no graceful shutdown.
- **"A native sidecar and the main container stop at the same time since they're in the same Pod."** Proven above with real per-container timestamps: the sidecar's `SIGTERM` arrived a full second *after* the main container had already exited.

<Callout title="The one-line takeaway">
A **Pod** is one or more containers sharing a network namespace (one IP, reachable over **localhost**) and optionally volumes; **init containers** run to completion in order before main containers start, and a plain `initContainers` entry with `restartPolicy: Always` becomes a **native sidecar** (GA since v1.33) that keeps running for the Pod's whole life with kubelet-managed startup/shutdown ordering — proven above, it also stops *last*, after every main container has exited. On deletion, endpoint removal and the `preStop` hook run **in parallel** (proven above: endpoints go not-ready in ~0.5s, well before a 5s `preStop` finishes), `SIGTERM` fires only once `preStop` returns, and the **whole** `terminationGracePeriodSeconds` budget — `preStop`'s own time included — is what stands between that and `SIGKILL`; setting it to `0` (proven above) skips graceful shutdown almost entirely, it does not make it faster. A Pod's phase (`Pending`/`Running`/`Succeeded`/`Failed`/`Unknown`) and its `restartPolicy` (`Always`/`OnFailure`/`Never`) govern the rest of its lifecycle, but a **bare Pod that dies is not recreated** — that job belongs to the controllers covered next.
</Callout>
