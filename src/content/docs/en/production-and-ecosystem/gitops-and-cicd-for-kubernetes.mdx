## The idea in one sentence

**GitOps** makes a Git repository the single source of truth for a cluster's desired state, with a reconciler running inside the cluster pulling and applying that state instead of a CI job pushing it from outside.

## Push-based CI/CD versus pull-based GitOps

A traditional CI/CD pipeline is **push-based**: a CI job builds an artifact, then runs `kubectl apply` or `helm upgrade` directly against the cluster, using cluster credentials the CI system holds itself. That works, but it means the CI system — often a third-party SaaS product outside your infrastructure boundary — needs standing, and often privileged, access to your cluster.

**GitOps** flips the direction. A reconciler such as Argo CD or Flux runs *inside* the cluster it manages, continuously watching a Git repository that holds the desired manifests or Helm values. When the repository changes, the reconciler pulls the new desired state and applies it itself — the cluster reaches out to Git, Git never reaches into the cluster.

```bash
# Push-based: CI applies directly, using credentials CI itself holds
kubectl apply -f manifests/
helm upgrade myapp ./mychart -f values-prod.yaml

# Pull-based (GitOps): CI's job stops at committing to Git;
# an in-cluster reconciler (Argo CD / Flux) takes it from there
git commit -am "bump myapp image tag to 1.5.0"
git push origin main
```

## Why the pull-based model earns its keep

Three concrete benefits fall out of moving the apply step inside the cluster:

- **No external system needs cluster-admin credentials.** The CI system's job ends at a `git push`; only the in-cluster reconciler, which you control, ever authenticates against the API server with write access.
- **Drift detection.** Because the reconciler continuously compares live cluster state against the Git-declared state, a manual out-of-band `kubectl edit` or `kubectl scale` gets noticed — and can be automatically reverted — instead of silently diverging from what Git says should be running.
- **An inherently auditable history.** Every change to desired state is a Git commit: who changed what, when, and why (via the commit message), all in the same history you already use for code review.

## A realistic pipeline shape

Building and deploying with GitOps splits into two repositories (or two clearly separated stages): one that builds the application, and one that declares what should be running.

```bash
# Stage 1 — application repo CI: build and publish the image
docker build -t myregistry/myapp:1.5.0 .
docker push myregistry/myapp:1.5.0

# Stage 2 — update the manifests/values repo that GitOps watches
# (a small CI step, or a bot, edits the tag and commits)
sed -i 's/tag: .*/tag: "1.5.0"/' values-prod.yaml
git commit -am "myapp: bump image tag to 1.5.0"
git push origin main

# From here, the GitOps reconciler (not CI) notices the commit and applies it.
# In a push-based setup, stage 2 would instead run directly against the cluster:
#   helm upgrade myapp ./mychart -f values-prod.yaml
```

The CI system never runs `kubectl` or `helm upgrade` against the live cluster in the GitOps flow — its responsibility ends at building the image and committing the new desired state to Git.

## `kubectl kustomize`: base + overlay, proven with a real hash-suffixed rename

Both Argo CD and Flux render plain Kubernetes manifests from a source tree before applying anything — Kustomize's base/overlay model is the most common shape for that source tree, and `kubectl kustomize` (Kustomize is built into `kubectl`) renders it with zero extra tooling. A base declares a Deployment and a `configMapGenerator` (deliberately **not** a literal `ConfigMap` in `resources:` — that would disable the hash suffix); a `prod` overlay patches replicas and layers an extra key onto the generated ConfigMap:

```text
$ kubectl kustomize base/
apiVersion: v1
data:
  LOG_LEVEL: info
kind: ConfigMap
metadata:
  name: orders-api-config-hf678c7m2b
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
spec:
  replicas: 1
  ...
      containers:
      - envFrom:
        - configMapRef:
            name: orders-api-config-hf678c7m2b
        image: myregistry/orders-api:1.0.0
        name: orders-api

$ kubectl kustomize overlays/prod/
apiVersion: v1
data:
  LOG_LEVEL: warn
kind: ConfigMap
metadata:
  name: orders-api-config-dfk4bdbtkk
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
spec:
  replicas: 5
  ...
      containers:
      - envFrom:
        - configMapRef:
            name: orders-api-config-dfk4bdbtkk
        image: myregistry/orders-api:1.0.0
        name: orders-api
```

Three things are proven at once here: the `replicas: 5` **strategic-merge patch** applied cleanly on top of the base's `replicas: 1`; the generated ConfigMap's name changed hash suffix (`-hf678c7m2b` → `-dfk4bdbtkk`) the moment its `data` changed (`LOG_LEVEL: info` → `warn`, via `behavior: merge` layering onto the base generator); and the Deployment's own `envFrom.configMapRef.name` was **rewritten automatically** to track the new hash both times, with no manual cross-reference update anywhere in the overlay. That automatic rename-and-rewire is exactly the mechanism that forces a real rolling update whenever a ConfigMap's *content* changes — no separate restart step, no `kubectl rollout restart` needed, because the Deployment's Pod template genuinely changed.

## Server-side apply is what Argo CD and Flux use under the hood

The [Server-Side Apply](/kubernetes/en/foundations/kubectl-and-declarative-yaml/) mechanism this course already covers for `kubectl apply --server-side` is not just an alternative reconcilers *could* use — it is the mechanism GitOps tools are built on, because a reconciler managing hundreds of resources across many source commits needs the API server's own conflict tracking (`managedFields`, named field managers) rather than a client-side three-way diff against a locally cached last-applied-configuration. This is not a docs claim taken on faith — it surfaced directly while installing Argo CD's own upstream manifest on this lesson's cluster:

```text
$ kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
...
The CustomResourceDefinition "applicationsets.argoproj.io" is invalid: metadata.annotations: Too long: may not be more than 262144 bytes

$ kubectl apply -n argocd -f install.yaml --server-side --field-manager=argocd-installer
...
Apply failed with 1 conflict: conflict with "kubectl-client-side-apply" using networking.k8s.io/v1: .spec.ingress
```

The first error is the well-known **client-side apply annotation size limit**: `kubectl apply`'s classic mode stuffs the entire applied object into a `kubectl.kubernetes.io/last-applied-configuration` annotation, and Argo CD's own CRDs are large enough to blow past etcd's 256KiB-ish annotation ceiling — which is exactly why Argo CD's and Flux's own install docs recommend `--server-side` for their own manifests. Switching to `--server-side` immediately surfaced the *second* real, named-field-manager conflict this course's foundations lesson already covers in depth: a NetworkPolicy's `.spec.ingress` already had a `kubectl-client-side-apply` field manager from the first (partially-successful) apply, and server-side apply refused to silently steal ownership of a field an existing manager still held — the same `--force-conflicts` escape hatch applies here as anywhere else server-side apply is used.

An `Application` custom resource (no `argocd` CLI needed — it is just a CRD instance) pointed at a real, public git repository proves a genuine end-to-end reconcile, no local git daemon required:

```yaml
# Application CRD instance -- argoproj.io is only installed on this lesson's own
# Argo CD cluster, not the shared harness cluster, so this excerpt carries no k8s/ path
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: guestbook
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/argoproj/argocd-example-apps.git
    targetRevision: HEAD
    path: guestbook
  destination:
    server: https://kubernetes.default.svc
    namespace: guestbook
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

```text
$ kubectl apply -f guestbook-app.yaml
application.argoproj.io/guestbook created

$ kubectl -n argocd get application guestbook -o jsonpath='{.status.sync.status} {.status.health.status}'
Synced Progressing    # a few seconds later:
Synced Healthy
```

## Drift detection and self-heal, proven by scaling out-of-band by hand

`syncPolicy.automated.selfHeal: true` is not just a claim in a values file — proven by manually scaling the reconciled Deployment behind Argo CD's back and watching it get reverted with no human re-running anything:

```text
$ kubectl -n guestbook get deployment guestbook-ui -o jsonpath='{.spec.replicas}'
1

$ kubectl -n guestbook scale deployment guestbook-ui --replicas=3
deployment.apps/guestbook-ui scaled

$ kubectl -n guestbook get deployment guestbook-ui -o jsonpath='{.spec.replicas}'
1
```

Within roughly ten seconds of the manual `scale`, `spec.replicas` was back to `1` — the value Git actually declares — entirely on Argo CD's own initiative. `syncPolicy.automated.prune: true` does the same thing for resources *removed* from Git: without it, deleting a manifest from the source repo leaves the corresponding cluster object orphaned forever, since a reconciler by default only ever adds and updates, never deletes, unless explicitly told to prune.

## Image update automation (docs-only — no image registry pushes in this lesson)

A full loop closes the pipeline shown earlier by letting the *reconciler* — not CI — pick up new image tags automatically: Flux's [image update automation](https://fluxcd.io/flux/guides/image-update/) guide describes three CRDs working together — an `ImageRepository` that scans a registry for new tags, an `ImagePolicy` that "select[s] the latest tag based on the defined policy (semver, calver, regex)," and an `ImageUpdateAutomation` that "replace[s] the tag in Kubernetes manifests" and commits the change back to Git itself, closing the loop without a human or CI job ever writing the new tag by hand. This course does not push real images to a registry, so this stays a docs citation rather than a proven run.

## CI pipeline shape, `kubectl diff` in CI, and linting the course's own manifests

A realistic CI pipeline for a GitOps-managed cluster has four stages: **build** the application image, **push** it to a registry, **bump** the image reference in the manifests/values repository (by hand, by a small script, or by the image-automation controller above), and let the reconciler **reconcile**. Two verification steps belong in that pipeline *before* anything reaches the reconciler:

- `kubectl diff -f <rendered manifests>` (or `kubectl kustomize overlays/prod | kubectl diff -f -`) — a real, live comparison against whatever is currently running, the same underlying mechanism as `kubectl apply --dry-run=server` proven throughout this course, catching an unintended field change (a dropped `resources.requests`, a `replicas` regression) before it merges.
- A static manifest linter, run with no local install via `docker run` or `npx` — proven directly against this lesson's own rendered `overlays/prod` output:

```text
$ kubectl kustomize overlays/prod > rendered-prod.yaml
$ docker run --rm -i ghcr.io/yannh/kubeconform:latest -summary - < rendered-prod.yaml
Summary: 2 resources found parsing stdin - Valid: 2, Invalid: 0, Errors: 0, Skipped: 0

$ docker run --rm -v "$(pwd):/work" -w /work stackrox/kube-linter:latest lint rendered-prod.yaml
Error: found 5 lint errors
KubeLinter 0.8.3
.../rendered-prod.yaml: (object: orders-api apps/v1, Kind=Deployment) object has 5 replicas but does not specify inter pod anti-affinity (check: no-anti-affinity, ...)
.../rendered-prod.yaml: (object: orders-api apps/v1, Kind=Deployment) container "orders-api" does not have a read-only root file system (check: no-read-only-root-fs, ...)
.../rendered-prod.yaml: (object: orders-api apps/v1, Kind=Deployment) container "orders-api" is not set to runAsNonRoot (check: run-as-non-root, ...)
.../rendered-prod.yaml: (object: orders-api apps/v1, Kind=Deployment) container "orders-api" has cpu request 0 (check: unset-cpu-requirements, ...)
.../rendered-prod.yaml: (object: orders-api apps/v1, Kind=Deployment) container "orders-api" has memory limit 0 (check: unset-memory-requirements, ...)
```

`kubeconform` confirms the manifests are structurally valid against the Kubernetes OpenAPI schema (schema-only — it has no opinion on security posture); `kube-linter` (or Polaris, a similar tool) catches exactly the production-hardening gaps [this course's own production checklist](/kubernetes/en/production-and-ecosystem/production-checklist-and-the-kubernetes-api-client/) names — missing anti-affinity, no read-only root filesystem, no non-root user, no resource requests/limits — against manifests this lesson wrote earlier in good faith. Both tools ran with zero local install, straight from their published container images, which is exactly how a CI runner would use them too.

## Mental Model

GitOps is not a new apply mechanism — proven throughout this lesson, it is the same `kubectl kustomize`/server-side-apply machinery this course already covers, just triggered by a Git watch loop instead of a human or a CI job. Everything distinctive about it falls out of *where the credentials live and who presses the button*: a reconciler inside the cluster with its own field manager, continuously diffing Git against live state (proven above with a real revert within seconds of an out-of-band `scale`), rather than an external CI job holding standing write access. Kustomize's base/overlay/generator model is the most common way to describe "what should be running" as a source tree Git can hold; the reconciler is just the thing that keeps making that source tree true.

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Push-based CI/CD | Simple, one pipeline does everything, no in-cluster component | Proven above conceptually: CI holds standing, often privileged, cluster credentials permanently |
| Pull-based GitOps (Argo CD/Flux) | Proven above: no external system needs cluster-admin, drift is caught and reverted automatically | Requires running and securing the reconciler itself inside the cluster |
| `configMapGenerator` (hash-suffixed) | Proven above: a content change forces a real rolling update automatically, no manual restart step | Every ConfigMap-referencing manifest must use the generated name, never a hardcoded one |
| `kubectl apply` (client-side, default) | Simple, no field-manager concepts to learn | Proven above with a real Argo CD install: large objects can blow past the `last-applied-configuration` annotation size limit |
| `--server-side` | Proven above: no annotation size limit, real field-manager conflict detection | Proven above: an existing client-side-applied field can produce a real conflict requiring `--force-conflicts` to resolve |
| `syncPolicy.automated.prune: true` | Deleting a manifest from Git actually removes the cluster object | A misconfigured selector or a manifest moved between Applications can prune more than intended — proven conceptually by the same mechanism that proved selfHeal above |

## Common Misconceptions

- **"GitOps means CI still applies changes, just after a Git commit."** Proven above: in the pipeline this lesson ran, the CI system's responsibility stopped at `git push` — the in-cluster Argo CD `Application` resource, not CI, performed every actual apply.
- **"Server-side apply is just an alternative flag, unrelated to how GitOps tools work."** Proven above with Argo CD's own install manifest: `--server-side` was required to get past a real annotation-size failure, and immediately surfaced a real field-manager conflict — this is the actual mechanism, not an incidental detail.
- **"selfHeal only matters for accidental changes, not deliberate ones."** Proven above: a deliberate, correctly-executed `kubectl scale` was reverted just as thoroughly as an accidental one — selfHeal does not distinguish intent, only divergence from Git.
- **"A GitOps reconciler removes resources deleted from Git automatically, by default."** Not proven true here — `prune: true` was explicitly set in this lesson's `syncPolicy`; without it, a reconciler only ever adds and updates, never deletes, leaving orphaned objects when a manifest is removed from source.
- **"A rendered manifest that passes kubeconform is production-ready."** Proven above: `kubeconform` reported 0 errors on this lesson's own overlay output, while `kube-linter` immediately found 5 real production-hardening gaps in the exact same manifests — schema validity and production-readiness are different, both-necessary checks.

## Reading AI-generated code

When reviewing generated CI/CD pipelines, Kustomize overlays, or GitOps Application manifests, check for:

- A CI pipeline step running `kubectl apply`/`helm upgrade` directly against a production cluster in a repo that also claims to be "GitOps" — proven above, real GitOps stops at committing to Git; a direct apply step from CI is push-based, not GitOps, no matter what the pipeline is named.
- A base `kustomization.yaml` with a literal `ConfigMap` in `resources:` *and* a `configMapGenerator` for the same name — proven above, `behavior: replace` on a directly-declared resource disables the hash suffix, defeating the automatic-rolling-update mechanism this pattern exists for.
- `patchesStrategicMerge` in a `kustomization.yaml` — proven above with a real, current `kubectl kustomize` run: `# Warning: 'patchesStrategicMerge' is deprecated. Please use 'patches' instead. Run 'kustomize edit fix' to update your Kustomization automatically.` It still renders correctly today (this course's `kustomize` v5.8.1 accepted it with only a warning), but AI-generated Kustomize output copying older examples should use the unified `patches:` field this lesson uses throughout instead.
- `kubectl apply -f <entire-repo-directory>` with no `--prune` (or a GitOps reconciler with pruning disabled) — proven above, without an explicit prune step a resource removed from source is never removed from the cluster, silently accumulating orphaned objects over time.
- A GitOps `Application`/`Kustomization` resource pointed at a CI system's service-account credentials, or a CI pipeline granted `cluster-admin` "to be safe" — proven above conceptually: the entire security benefit of GitOps depends on the external CI system specifically *not* holding standing cluster-admin access; a CI SA with `cluster-admin` recreates the exact problem GitOps exists to remove.
- A rendered-manifest CI gate that only runs schema validation (kubeconform) and calls it "production-ready" — proven above, kube-linter found real, separate hardening gaps kubeconform's schema check has no way to catch.

<SpotTheBug code={`# kustomization.yaml is a Kustomize build input, never applied to the API server directly -- no k8s/ path
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
  - configmap.yaml
configMapGenerator:
  - name: orders-api-config
    behavior: replace
    literals:
      - LOG_LEVEL=info`}>
`configmap.yaml` is a literal `ConfigMap` already declared in `resources:`, and the generator uses `behavior: replace` against the same name. Proven above with the equivalent setup: `behavior: replace` (and a directly-declared resource of the same name) produces a ConfigMap with **no hash suffix** — `orders-api-config`, not `orders-api-config-hf678c7m2b`. That means a content change to `LOG_LEVEL` never changes the object's name, so nothing forces the Deployment's Pods to roll — a config change silently fails to propagate to already-running Pods until something else (a manual rollout restart) happens. The fix is to drop the literal `configmap.yaml` from `resources:` and let the generator create it fresh (default `behavior`, which does add the hash suffix and auto-updates every `envFrom`/`volumes` reference to it).
</SpotTheBug>

<Callout title="The one-line takeaway">
**GitOps** treats a Git repository as the single source of truth for desired cluster state, with an in-cluster **reconciler** (Argo CD, Flux) continuously pulling and applying that state — proven above with a real Argo CD install, a real public-repo reconcile to `Synced`/`Healthy`, and a real out-of-band `scale` reverted by **selfHeal** within seconds. That reconciler is built on the exact same **Kustomize** rendering (base/overlay/`configMapGenerator` hash-suffix-and-rewire, proven above) and **Server-Side Apply** (proven above via a real client-side-annotation-size failure and a real field-manager conflict) this course already covers elsewhere — GitOps changes *who* applies and *from where*, not the underlying apply mechanism. A CI pipeline in this model stops at build-push-commit; `kubectl diff` and a schema linter (`kubeconform`) plus a hardening linter (`kube-linter`, proven above to catch real gaps kubeconform cannot) belong before the reconciler ever sees a change, and Flux's image-update-automation CRDs (docs-only here) can close the loop entirely by having the reconciler itself write the new image tag back to Git.
</Callout>
