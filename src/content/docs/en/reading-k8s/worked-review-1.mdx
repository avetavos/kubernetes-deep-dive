## The feature

The prompt was: *"Deploy a web app behind a Service and an Ingress, with an HPA so it scales under load."* What follows is the kind of first draft an AI assistant hands back for exactly that prompt — every file looks like something copied from a slightly old tutorial, and the object shapes are individually plausible. Read it the way the [review checklist](/kubernetes/en/reading-k8s/review-checklist/) recommends: apply-time correctness first (does the API server even accept this), then rollout behaviour, then traffic shape. It has **7 real bugs**; check the [AI bug catalog](/kubernetes/en/reading-k8s/ai-bug-catalog/) for the general pattern behind each one. Every claim below was proven on a real two-node `kind` cluster (`kind create cluster --name reading-b`, Kubernetes 1.37.0, `metrics-server` patched with `--kubelet-insecure-tls`) — real `kubectl apply`, real `kubectl describe`/`get events`, real endpoint and probe behaviour.

## The review walk

### Deployment: an `apiVersion` that was removed years ago

`apps/v1beta1` is exactly the pre-1.16 Deployment shape a stale training example still uses. Proven directly against the API server:

```text
$ kubectl apply -f deployment.yaml
error: resource mapping not found for name: "web-app" namespace: "wr1" from "deployment.yaml": no matches for kind "Deployment" in version "apps/v1beta1"
ensure CRDs are installed first
```

<SpotTheBug code={`apiVersion: apps/v1beta1
kind: Deployment`}>
This isn't a deprecation warning, it's a hard removal — `apps/v1beta1` and `apps/v1beta2` stopped being served in Kubernetes 1.16, moved to `apps/v1`. The API server has no route for this group/version at all, so `kubectl` never even reaches schema validation; it fails at REST-mapping time, before the object is looked at. The fix is simply `apiVersion: apps/v1` — the rest of the Deployment's shape under `apps/v1` is unchanged.
</SpotTheBug>

### Service: a `selector` that doesn't match the Deployment's own Pods

The Service selects `app: web-app, tier: backend`; the Deployment's Pod template is labeled `app: web-app, tier: frontend`. Both objects apply cleanly — the API server never cross-checks a Service's selector against any Deployment. Proven with real endpoints after both the Deployment and Service were applied and the Pods were `2/2 Running`:

```text
$ kubectl get endpoints web-app
Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice
NAME      ENDPOINTS   AGE
web-app   <none>      24s

$ kubectl get endpointslices -l kubernetes.io/service-name=web-app
NAME            ADDRESSTYPE   PORTS     ENDPOINTS   AGE
web-app-985wj   IPv4          <unset>   <unset>     24s
```

<SpotTheBug code={`selector:
  app: web-app
  tier: backend`}>
Every field here is individually valid YAML and a legal Service selector — there is nothing for schema validation to reject. The Service is simply selecting a set of Pods that happens to be empty, and it stays that way silently: `kubectl get svc` shows the Service as healthy, the Deployment shows `3/3` Ready, and the only visible symptom is an EndpointSlice with zero addresses. The fix is making the two labels agree — either `tier: frontend` on the selector, or dropping the `tier` key from the selector entirely if it isn't needed to disambiguate.
</SpotTheBug>

### Deployment: no `resources.requests` at all, so the HPA can never work

The container has no `resources` block whatsoever. Both the Deployment and the HPA apply cleanly — this only surfaces once the HPA actually tries to compute a percentage. Proven with a real HPA against this exact Deployment on `metrics-server`:

```text
$ kubectl get hpa web-app-hpa
NAME          REFERENCE                TARGETS              MINPODS   MAXPODS   REPLICAS   AGE
web-app-hpa   Deployment/web-app-hpa   cpu: <unknown>/60%   2         10        2          35s

$ kubectl describe hpa web-app-hpa
...
  Type            Status  Reason                   Message
  ----            ------  ------                   -------
  ScalingActive   False   FailedGetResourceMetric  the HPA was unable to compute the replica count: failed to get cpu utilization: missing request for cpu in container web-app of Pod web-app-hpa-f94bdb95c-knmc2
Events:
  Warning  FailedGetResourceMetric  failed to get cpu utilization: missing request for cpu in container web-app of Pod web-app-hpa-f94bdb95c-knmc2
```

<SpotTheBug code={`containers:
- name: web-app
  image: nginx:alpine
  ports:
  - containerPort: 80`}>
A subtlety worth knowing before you go looking for this bug in a real manifest: setting `resources.limits.cpu` **without** `resources.requests.cpu` does **not** reproduce this error — the API server defaults an unset CPU request to match the CPU limit the moment any limit is present (confirmed directly: applying a container with only `limits: { cpu: 500m }` came back with `requests: { cpu: 500m }` already filled in). The real bug is a container with **no `resources` block at all** — `{}` on the wire, confirmed via `kubectl get pod -o jsonpath='{.spec.containers[0].resources}'`. HPA's utilization math is always requests-relative and never falls back to limits; with truly no request, `metrics-server` has nothing to divide by, and `kubectl get hpa` reports `<unknown>` forever. The fix is adding an explicit `resources.requests.cpu` (and, separately, a `resources.limits` for good QoS hygiene) to the container.
</SpotTheBug>

### Deployment: the same endpoint for liveness and readiness

Both probes hit `GET /` on port 80 every 3 seconds with `failureThreshold: 1`, and there is no `startupProbe`. Proven with a slow-starting container (20-second warm-up) using this exact probe shape:

```text
$ kubectl describe pod slow-warm-bad
Events:
  Type     Reason     Age                From      Message
  ----     ------     ----               ----      -------
  Warning  Unhealthy  15s (x2 over 33s)  kubelet   Liveness probe failed: Get "http://10.244.1.11:8080/": dial tcp 10.244.1.11:8080: connect: connection refused
  Normal   Killing    15s (x2 over 33s)  kubelet   Container web failed liveness probe, will be restarted
  Warning  Unhealthy  3s (x15 over 35s)  kubelet   Readiness probe failed: Get "http://10.244.1.11:8080/": dial tcp 10.244.1.11:8080: connect: connection refused

$ kubectl get pod slow-warm-bad
NAME            READY   STATUS    RESTARTS     AGE
slow-warm-bad   0/1     Running   2 (0s ago)   50s
```

<SpotTheBug code={`livenessProbe:
  httpGet: { path: /, port: 80 }
  periodSeconds: 3
  failureThreshold: 1
readinessProbe:
  httpGet: { path: /, port: 80 }
  periodSeconds: 3
  failureThreshold: 1`}>
A liveness probe answers "is this container stuck and needs a restart"; a readiness probe answers "should traffic reach this container right now." Pointing both at the same endpoint with no `startupProbe` erases that distinction: a container that is merely still warming up looks identical, to the kubelet, to one that is permanently wedged — and it gets killed for a condition a restart cannot fix, since restarting resets the warm-up clock to zero, confirmed above by real, repeating restarts (`RESTARTS: 2 (0s ago)` and climbing). The fix is a dedicated `startupProbe` (which fully disables liveness/readiness until it succeeds once) sized for the real worst-case startup time, plus a liveness probe that is meaningfully more tolerant than readiness once startup is done.
</SpotTheBug>

### Deployment: no `preStop`, so a rolling delete can drop an in-flight request

There is no `lifecycle.preStop` on the container. Proven with a real Service + a client pod curling in a loop while the serving Pod is deleted mid-loop, 40 requests at 250ms intervals, delete issued after request 8:

```text
$ kubectl exec loadgen -- sh -c 'for i in $(seq 1 40); do wget -q -T1 -O /dev/null -S http://web-app/ 2>&1 | grep -o "HTTP/[0-9.]* [0-9]*"; sleep 0.25; done' &
$ kubectl delete pod web-app-<hash>
```

```text
# request  status (no preStop)
8   HTTP/1.1 200
9   HTTP/1.1 200
10  (no response -- connection refused/reset)
11  HTTP/1.1 200
...
39/40 succeeded, exactly 1 request lost, timed right at the delete
```

The identical test against a Pod with `preStop: sleep 5` added showed the one failure move to request #1 (a pre-delete cold-start blip, unrelated to termination) — every request from the delete point onward succeeded, `40/40` from that point on.

<SpotTheBug code={`containers:
- name: web-app
  image: nginx:alpine
  # no lifecycle.preStop here`}>
`kubectl delete pod` sends SIGTERM to the container roughly in parallel with removing the Pod from the Service's Endpoints — it does **not** wait for every kube-proxy on every node to finish reprogramming iptables/ipvs first. Without a `preStop` hook, nginx can stop accepting new connections before that endpoint-removal has propagated everywhere, so a request routed in that narrow window fails. A `preStop` hook that just sleeps a few seconds does nothing to the Service or endpoint machinery at all — it only keeps the container's listening socket open a little longer, which is enough, proven above, to absorb the exact same race that dropped a request without it. The fix: `lifecycle.preStop.exec.command: ["sh", "-c", "sleep 5"]` plus a `terminationGracePeriodSeconds` large enough to contain it.
</SpotTheBug>

### Deployment: `maxUnavailable: 0` and `maxSurge: 0` together

Both knobs are set to `0` in the same `rollingUpdate` block. Proven directly against the API server:

```text
$ kubectl apply -f deployment-zerozero.yaml
The Deployment "web-app-zz" is invalid: spec.strategy.rollingUpdate.maxUnavailable: Invalid value: 0: may not be 0 when `maxSurge` is 0
```

<SpotTheBug code={`strategy:
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 0`}>
This looks like "maximally safe" to someone reading the field names in isolation — zero unavailable, zero surge, what could roll wrong? The API server rejects it outright, because together they describe a rollout with no legal way to make progress at all: it can't take a Pod down (`maxUnavailable: 0`) and it can't bring a new one up first either (`maxSurge: 0`). At least one of the two must be non-zero. The fix is picking the actual trade-off intended — `maxUnavailable: 0, maxSurge: 1` for zero-downtime at the cost of one extra Pod during rollout, or `maxUnavailable: 1, maxSurge: 0` for no extra capacity at the cost of one Pod missing briefly.
</SpotTheBug>

### Ingress: the pre-1.19 `v1beta1` shape

```text
$ kubectl apply -f ingress.yaml
error: resource mapping not found for name: "web-app" namespace: "wr1" from "ingress.yaml": no matches for kind "Ingress" in version "networking.k8s.io/v1beta1"
ensure CRDs are installed first
```

<SpotTheBug code={`apiVersion: networking.k8s.io/v1beta1
...
backend:
  serviceName: web-app
  servicePort: 80`}>
Same class of bug as the Deployment's `apps/v1beta1`: this is the Ingress shape from before Kubernetes 1.19, and both the API version and the `backend.serviceName`/`backend.servicePort` field names were removed, not merely deprecated. The fix is `networking.k8s.io/v1`, with `pathType` now required and the backend written as `backend.service.name`/`backend.service.port.number` — or, given the Ingress API's frozen status and ingress-nginx's retirement, migrating to Gateway API's `HTTPRoute` instead of updating in place.
</SpotTheBug>

## The corrected code

```yaml
# k8s/worked-review-1/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
        tier: frontend
    spec:
      terminationGracePeriodSeconds: 15
      containers:
      - name: web-app
        image: nginx:alpine
        ports:
        - containerPort: 80
        resources:
          requests: { cpu: 100m, memory: 64Mi }
          limits: { cpu: 250m, memory: 128Mi }
        startupProbe:
          httpGet: { path: /, port: 80 }
          periodSeconds: 2
          failureThreshold: 15
        readinessProbe:
          httpGet: { path: /, port: 80 }
          periodSeconds: 3
          failureThreshold: 1
        livenessProbe:
          httpGet: { path: /, port: 80 }
          periodSeconds: 10
          failureThreshold: 3
        lifecycle:
          preStop:
            exec:
              command: ["sh", "-c", "sleep 5"]
```

## Mental Model

Two of these seven bugs (1, 7) are the API server refusing to even recognize the object — a stale training example using an API version that was removed years ago, caught instantly and loudly. The other five all apply cleanly and only fail later, each because the manifest made a claim about *something outside the file itself* that nothing at apply time checks: that a Service's selector actually matches a real Deployment's Pod labels, that a container's resource footprint is declared for an autoscaler that needs it, that "responding" and "ready for traffic" are the same question for this specific app, that the Service's endpoint bookkeeping is fast enough to never need a grace window, and that a rollout strategy which sounds maximally cautious is actually a legal combination at all. None of these five produce an error anywhere — they only show up as a real, but silent, gap between what `kubectl get` reports (all green) and what actually happens to real traffic.

## Common Misconceptions

- **"If `kubectl apply` succeeds, the objects are wired together correctly."** Proven above: a Service with a selector that matches nothing applies exactly as cleanly as one that matches everything — the API server never cross-validates a Service against any Deployment.
- **"A container with `resources.limits` set is safe for HPA even without `resources.requests`."** Proven above by direct API-server behavior: a `limits.cpu` with no `requests.cpu` gets `requests.cpu` **defaulted to match the limit** — the real HPA-breaking bug is a container with no `resources` block at all, not "limits but no requests."
- **"A `preStop` hook fixes a dropped-connection bug by telling the Service to stop routing here."** Proven above: `preStop` does nothing to Service/endpoint machinery — it only keeps the container's own listening socket open a little longer, which happens to be enough time for the real (separate, asynchronous) endpoint removal to finish propagating.
