## What this module is for

Every earlier module in this course taught you to *use* Kubernetes: writing manifests, applying them with `kubectl`, reading back status, scaling, scheduling, securing, storing, networking, and shipping with Helm/GitOps. None of it required knowing what the API server actually does with a request between "you typed `kubectl apply`" and "the object exists," how a controller actually finds out something changed, what a `kube-scheduler` plugin actually is under the extension-point names you have already seen, what order admission webhooks and `ValidatingAdmissionPolicy` actually run in, or what `managedFields` really tracks when two tools apply the same object.

That gap is exactly where AI-generated Kubernetes tooling fails in ways that look fine on the surface: a controller written with `List` in a `for`-loop instead of a shared informer, silently polling and missing events between polls; a reconcile function with no rate limiting that hot-loops on a permanent error; a webhook assumed to run "before validation" when the real chain interleaves mutating and validating differently; a script that "fixes" a `managedFields` conflict by force-taking every field instead of reading which one is actually contested. None of these are syntax errors. None of them are caught by `kubectl apply --dry-run=client`. All of them are facts about the runtime this whole module makes provable.

This module has one job: give you five pieces of runtime knowledge that let you look at **someone else's Kubernetes code or YAML** — a controller, a webhook config, a scheduler profile, a script full of `kubectl apply --server-side` calls — and answer:

1. **What actually happens to a request inside the API server, and how does a watch really work?** (the API server and etcd — `resourceVersion`, watch, bookmarks, `410 Gone`, and etcd as the one place state lives)
2. **How does a controller actually learn "something changed," without polling?** (controllers, informers, and workqueues — Reflector → DeltaFIFO → Indexer/Lister → workqueue → reconcile, straight from `client-go`)
3. **What is a scheduler "plugin," concretely, and in what order do they run?** (the scheduler framework — the real extension-point interfaces and the real plugin names from `pkg/scheduler`)
4. **What order do mutating webhooks, schema validation, validating webhooks, and `ValidatingAdmissionPolicy` actually run in?** (the admission chain — proven with a real chain, a real dry-run, and the exact source that decides the order)
5. **What does `managedFields` actually track, and what does "conflict" really mean?** (Server-Side Apply internals — the `f:`/`k:`/`v:` markers, `x-kubernetes-list-type`, and the `structured-merge-diff` library that makes it work)

Every claim in this module is backed by one of three things: the real Kubernetes source at [github.com/kubernetes/kubernetes](https://github.com/kubernetes/kubernetes), tag **v1.37.0** (this course's pinned version), cited by file and line; the official docs at [kubernetes.io/docs](https://kubernetes.io/docs/); or a real, reproduced run against a live 3-node `kind` cluster (`kind create cluster --name internals`, 1 control-plane + 2 workers, Kubernetes 1.37.0) — a real `kubectl -v=8` trace, a real `etcdctl get`, a real scheduler log, a real API-server error — pasted below the claim, never a guess about internals.

<Callout title="The one-line takeaway">
This module doesn't add new Kubernetes APIs — it explains the five mechanisms every manifest, controller, and script actually runs through: the **API server** (a stateless HTTP layer over **etcd**, the only place cluster state actually lives — reads are a `resourceVersion`-stamped list-then-watch, never a raw poll), the **informer pattern** (`client-go`'s Reflector → DeltaFIFO → Indexer/Lister → workqueue → reconcile, the shape every controller in this course's Deployment/ReplicaSet chain and every custom controller you will ever write actually has), the **scheduler framework** (a pipeline of named plugins at fixed extension points — `PreFilter`/`Filter`/`PostFilter`/`PreScore`/`Score`/`Reserve`/`Permit`/`PreBind`/`Bind`/`PostBind` — not a monolithic black box), the **admission chain** (mutating admission, then schema/strategy validation, then validating admission — each phase itself an ordered chain of in-tree plugins, `MutatingAdmissionPolicy`/`ValidatingAdmissionPolicy`, and webhooks, in an order fixed by the API server's own source), and **Server-Side Apply** (per-field ownership tracked in `managedFields`, computed by the `structured-merge-diff` library against the live OpenAPI schema's `x-kubernetes-list-type`/`x-kubernetes-map-type` markers). Every one of the five is either on kubernetes.io/docs or directly readable in `kubernetes/kubernetes` — unfamiliar, not undocumented.
</Callout>

## Mental Model

Everything in this module is one story told from five different points on the same loop: **you send a mutation, the API server runs it through a fixed pipeline (auth, admission, validation, storage) and writes exactly one copy of the truth to etcd; every other component — a controller, the scheduler, `kubectl get -w` — finds out about that write the same way, by watching a `resourceVersion`-ordered stream from that one API server, never by polling, never by talking to etcd directly.** A controller is nothing more than "watch, queue, reconcile" wired through `client-go`'s informer machinery; the scheduler is nothing more than one more consumer of that same watch stream, running a pipeline of named plugins before it writes its own decision back through the same API server; admission and Server-Side Apply are both just extra structure the API server imposes on the write path itself, before anything reaches etcd. Once you can place any given fact in this module against that one loop, "how does Kubernetes actually work" stops being five separate things to memorize.

## Common Misconceptions

- **"A controller polls the API server on an interval to check for changes."** [Controllers, Informers, and Workqueues](/kubernetes/en/k8s-internals/controllers-informers-and-workqueues/) proves the opposite with a real, running informer: it lists once, then holds a long-lived HTTP watch connection and reacts to individual `ADDED`/`MODIFIED`/`DELETED` events — the periodic full `List` you may have heard of is a much longer **resync**, a safety net, not the primary mechanism.
- **"Admission webhooks all run in one undifferentiated pool, in registration order."** [Admission Chain](/kubernetes/en/k8s-internals/admission-chain/) proves the real order straight from `pkg/kubeapiserver/options/plugins.go`: mutating admission (in-tree plugins, then `MutatingAdmissionPolicy`, then `MutatingAdmissionWebhook`) all completes, then schema/strategy validation runs, then validating admission (in-tree, `ValidatingAdmissionPolicy`, `ValidatingAdmissionWebhook`) runs — two genuinely separate phases, not one pool.
- **"The scheduler is a black box that just picks a node."** [Scheduler Framework](/kubernetes/en/k8s-internals/scheduler-framework/) proves it is a pipeline of separately named, separately swappable plugins — real names straight from `pkg/scheduler/framework/plugins/names`, at fixed extension points defined in `k8s.io/kube-scheduler/framework`.
- **"`managedFields` is basically the same idea as the old `last-applied-configuration` annotation, just server-side."** [Server-Side Apply Internals](/kubernetes/en/k8s-internals/server-side-apply-internals/) proves they are structurally different: `managedFields` is a per-manager, per-field ownership map keyed by real OpenAPI schema markers (`x-kubernetes-list-type: map` vs `atomic`), computed by the `structured-merge-diff` library — not a single stashed blob of "what I applied last time."

## Reading AI-generated code

The whole point of this module is this section, five times over — one per lesson. As a preview, here is the survey-level version: a snippet that looks like a correct controller and is missing the one thing that makes it a controller rather than a poller.

<SpotTheBug code={`// A "controller" a teammate wrote to react to Pod changes
setInterval(async () => {
  const pods = await api.listNamespacedPod('default');
  for (const pod of pods.body.items) {
    reconcile(pod);
  }
}, 5000);`}>
This runs `reconcile` on every Pod every 5 seconds, forever, whether anything changed or not — proven wrong by [Controllers, Informers, and Workqueues](/kubernetes/en/k8s-internals/controllers-informers-and-workqueues/): a real controller uses a **watch**, delivered as individual `ADDED`/`MODIFIED`/`DELETED` events through a Reflector into a DeltaFIFO, and reconciles only the object whose key was actually enqueued. This `setInterval` version reconciles every object on every tick regardless of whether it changed (wasted API server load that scales with cluster size, not with the change rate), and — worse — it can **miss** a change entirely if an object is created and deleted again inside one 5-second window, since nothing about polling guarantees you see every intermediate state the way an ordered watch stream does.
</SpotTheBug>
